# M13 part E, continued: a CSV file for Jira, and the keys back (as built)

Built 2026-11-20. The product owner asked for an optional CSV file that someone can import into Jira, possibly linked to the GitHub items, and left the shape to us. Part E (`M13_JIRA.md`) already carries a Jira key from a slice to its issue, cell, pull request and change record. This adds the way in (a file Jira's own importer reads) and the way back (the keys Jira gave, recorded on the slices and epics). MACH still never calls Jira, holds no Jira credentials and reads nothing from Jira except a file a person hands it.

## What was decided, and why

1. **One file, chosen per Jira.** Both platforms can keep epic-to-story in one file, but by different columns: Cloud by `Work item ID` and `Parent` (Epic Link is deprecated there), Data Center by `Epic Name` and `Epic Link`. A single file that carries both would put a deprecated column in front of Cloud users and an unknown one in front of Data Center users, so `--flavour cloud|data-center` chooses (Cloud by default). Each is one self-contained file; two files were not needed.
2. **Rows: epics, then their stories, in the product manager's order.** Epics in ID order; within each, the order `slice move` set (`handoff.order_rows`), which is the builders' order. A parent is always before its children, as both platforms ask.
3. **Stable numeric row IDs.** `1000000 + n` for `EPIC-n`, `2000000 + n` for `SLICE-n`: numbers, because the Cloud KB says the Parent column takes the numeric ID, and the same item has the same ID in every export. On Data Center, where an Issue Id becomes an External issue ID, importing the same file twice therefore skips what was already imported, instead of making duplicates.
4. **What goes in by default: slices marked ready or further** (approved, ready to build, being built, the builders' question, shipped). A draft is not agreed work. `--state all` adds drafts, interviews and those awaiting approval; superseded slices never go in. An epic goes in when it has a slice in the file (with `--state all`, every epic). A slice that is on GitHub but not in this workspace is left out (its spec is not here) and listed.
5. **Items that already have a Jira key are left out and listed, never updated.** Updating by key is possible, but on Data Center every column the file leaves out is reset to its default, on Cloud the non-administrator import may not offer the key, and any update would overwrite what people have since written in Jira. A slice whose epic is already in Jira is still exported, with no Parent (a Parent naming an existing issue fails on Cloud, JRACLOUD-83611) and a line in its description: "Epic: EPIC-001 (...), already in Jira as KEY-1: set it as this item's parent there."
6. **The description is wiki markup**, the form the evidence says the importer stores (JRACLOUD-79205, the ordered-list KB). It carries a header line (MACH ID, revision, epic), the GitHub issue as a wiki link, what the slice depends on (with their Jira keys where known), then `h3. Why` (the why's section from `intent.md`) and `h3. Scenarios` (the spec's `### Scenarios`). Markdown headings, bullet and numbered lists, bold, inline code and tables are converted; every other `{ } [ ] | \` is escaped, so no macro, link or mention (`[~name]`) can be formed from spec text, and a line that would read as a heading, quote or rule is escaped. Each piece is cleaned, redacted with `issue_rules.bound_text` (the shared redaction) and bounded (why 8,000, scenarios 18,000, the whole description 30,000 characters); a cut says so. Links in the spec become `text (url)`, never a live link.
7. **The GitHub link: a URL column plus a line in the description.** CSV cannot make a web link, so `GitHub issue` holds the issue's address (built from the repository and number in the ledger, never from issue text) for a URL custom field, and the description repeats it. Jira's GitHub integration links the pull requests and commits itself, through the key part E puts in the pull request's title and the merge commit, once `jira keys` has recorded it; the export does not try to do that work.
8. **Labels**: `mach`, the MACH ID (`SLICE-001`, `EPIC-001`) and, for a story, its place (`mach-ready_to_build`, `mach-draft`, ...). Each is cleaned to letters, digits, `_`, `.` and `-`. `labels = mach` finds everything in Jira, and the MACH ID label is how `jira keys` matches a row when there is no MACH ID field.
9. **`MACH ID`**, a column of its own for a short text custom field, is the stable external ID; it is also a label so nothing depends on creating the field.
10. **Dependencies**: a `Blocks` column on the depended-on row naming the dependent row's ID (the row blocks the value, as the Data Center KB describes outward links); only when both are in the file. Always also written in the description, since the Cloud value format is not documented. The README says to leave it unmapped where the screen does not offer it.
11. **No setting.** The project, the work type names and the date format are all chosen on the import screen ("Map field value" maps Epic and Story to the project's own names), so the file names none and `.factory/config.json` gains nothing. The README says so.
12. **Formula cells**: following OWASP, a cell is prefixed with a single quote when it starts (after any spaces) with `=`, `@`, tab, carriage return, line feed or their full-width forms, or with `+` or `-` followed anywhere by `=`, `(`, `)`, `|`, `!` or `@`. A leading sign with none of those cannot call a function or reach another sheet or program, so a summary such as `- Fix the sign-in page` or `-1` is left as written; this narrowing is our reading, not OWASP's words. Every field is quoted. Jira keeps the quote, which the README says. Excel can undo a quote when the file is saved again, as OWASP warns; the file is meant to go straight to Jira.
13. **Bytes**: UTF-8 with no byte order mark (a mark could end up in the first column's name), RFC 4180 quoting, CRLF between records and `\n` inside a cell, no time or random value anywhere, so the same workspace and the same last refresh give the same bytes.
14. **Where it is written**: `.factory/studio/jira/<flavour>[-EPIC-NNN][-all]/mach-jira.csv` and `README.txt`, inside the git-ignored workspace. `--out` may name a folder inside that workspace or outside the repository; a folder anywhere else in the repository is refused, judged by where a symbolic link leads.
15. **The keys back**: after the import, someone exports the items from Jira as CSV (Jira names the column "Issue key" or "Work item key", a custom field "Custom field (MACH ID)", and repeats "Labels"). `jira keys <file>` matches each row by its MACH ID column, else by the one `SLICE-`/`EPIC-` label it carries, validates the key with `issue_rules.is_jira_key`, and records it through `link_slice` / `link_epic`, the helpers `slice link` and `epic link` now share. A slice marked ready is not changed: it is listed under `needs_reopening` (the same rule as `slice link`). An epic is linked, and the slices already marked ready that would carry its key are named. A different key already stored is refused (change it with `slice link` / `epic link`); one MACH ID with two keys, or one key on two items, is refused for each; rows naming no MACH item or several are listed by row number. The file is bounded (8 MiB, 5,000 rows, 500 columns), must be UTF-8, and is read as data only: a bad key is never echoed and nothing in it is followed. `--dry-run` says what would be linked and changes nothing.

## The columns

Cloud (`--flavour cloud`, the default):

| Column | Rows | Holds | Map to |
|--------|------|-------|--------|
| `Work item ID` | all | stable number (decision 3) | Work item ID |
| `Work type` | all | `Epic` or `Story` | Work type |
| `Summary` | all | the title, one line, at most 250 characters | Summary |
| `Parent` | stories | the epic's `Work item ID` when the epic is in the file | Parent |
| `Description` | all | wiki markup (decision 6) | Description |
| `Labels` (repeated) | all | `mach`, MACH ID, place | Labels |
| `MACH ID` | all | `EPIC-NNN` / `SLICE-NNN` | a text custom field, or unmapped |
| `GitHub issue` | where there is one | `https://github.com/OWNER/REPO/issues/N` | a URL custom field, or unmapped |
| `Blocks` (repeated, only when needed) | depended-on rows | the dependent rows' IDs | the Blocks link type, or unmapped |

Data Center (`--flavour data-center`): `Issue Id`, `Issue Type`, `Summary`, `Epic Name` (epics: `EPIC-NNN <title>`, at most 100 characters, unique by its ID), `Epic Link` (stories: their epic's Epic Name), `Description`, `Labels`..., `MACH ID`, `GitHub issue`, `Blocks`....

## Not built

- The visual app (`apps/studio`, `web/`) neither exports nor takes keys back; its host runs a fixed list of operations, which does not include these.
- Updating Jira items by key (decision 5), sub-tasks, components, versions, assignees, priorities, statuses, sprints or dates: the slice has none of these, and Jira sets its own.
- A web link (remote link) to the GitHub issue: CSV cannot make one.
- Linking to an epic already in Jira from the file: it is named in the description for a person to set.
- A Jira JSON import, the Jira REST API, or any call to Jira; reading Jira other than a file a person hands over.
- Matching Jira rows by summary: summaries are not unique, so only the MACH ID column or label counts.

## How far tested

`tests/test_jira_export.py`, 19 tests on the stand-in GitHub used by the other Studio tests:

- formula cells: `=`, `@`, `+`/`-` with a function, a pipe or a full-width form, a leading tab, carriage return, line feed or spaces, all prefixed; `- Fix the sign-in page`, `-1`, `-1+1`, a hyphen with a comma, IDs and labels left alone; the quote taken off on the way back;
- Markdown to wiki markup, and escaping that leaves no `[~` mention, `{macro}` or heading-looking line; labels without spaces;
- a Cloud file: header, epic then stories, row IDs, Parent, Blocks for a dependency, labels, the MACH ID and GitHub columns, the why and the scenarios, the dependency line, a draft left out and listed, the README's screen, columns and way back, and no GitHub call;
- the file parses with `csv`, every row has the header's width, writing it again gives the same bytes, no byte order mark, doubled quotes, CRLF records and line breaks inside a cell;
- `--state all` with drafts, in the order `slice move` set, and a summary starting with a hyphen unchanged; Data Center's Epic Name and Epic Link; one epic, an epic with no slices, an unknown epic refused;
- the same bytes from two exports and from another folder; folders in the tracked tree, the repository root, `.factory/release` and a symbolic link leading into the repository refused, outside and inside Studio's folder accepted, the product manager's checkout unchanged;
- a formula title neutralised, a secret in the why redacted, email addresses in scenarios masked; a long why cut and said so;
- items with keys left out and listed, a story under a keyed epic with no Parent and a description naming the key;
- `jira keys`: a dry run changes nothing; linked, already linked, needs reopening (a ready slice is not changed), unmatched by row and by unknown ID, a malformed key refused and not echoed, epics with ready slices named, the workspace still valid, no GitHub call; two keys for one item, one key for two items and a different stored key refused; a file too large, too many rows, no key column, not UTF-8 or missing refused; export, keys back, and a second export that is empty because everything is in Jira;
- isolation: `jira_export.py` imports no network, process or shell library and calls no Git or `gh`, uses `handoff.py` only to read, and changes Studio only through the link helpers; `tests/test_mach_product_isolation.py` and `tests/test_jira.py` cover it with the other Studio files.

**It has not been imported into a real Jira**, Cloud or Data Center. The column names, the Parent and Epic Link behaviour, the wiki markup and the Blocks column are as Atlassian's pages describe them, not as observed. A first import into a test project is the check that remains.
