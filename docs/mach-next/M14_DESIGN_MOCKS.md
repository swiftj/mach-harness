# M14 part C: design mocks (as built)

Design: `docs/mach-next/M14_DESIGN.md`, part C. Built 2026-11-20. A product manager attaches an approved picture of the screen to an interface slice; the picture is bound into the approval by its SHA-256, reaches the Factory as a file checked by hash and by content, sits in the cell, and the verifier records the built screen beside it. MACH never makes a picture, never fetches one from an address and never takes one from issue text. The scenarios stay the authority: a mock never adds a requirement. A slice without mocks behaves exactly as before.

## How the picture's bytes reach the Factory (the hard point)

An issue cannot carry a binary file through `gh` in a form MACH can verify: there is no API to attach one, and anything pasted or linked would be issue text or an address, both of which MACH treats as data and never fetches. So:

1. **The issue names, the repository carries.** The slice issue names each picture by SHA-256 only (marker digest, one line per picture, and the approval of the digest). The picture itself travels in the one place MACH already reads product files from with Git and nothing else: `product/ready/SLICE-NNN/`, on the integration branch, at the newest commit the local branch shares with the remote (`product_commit`, as for ready folders).
2. **For an issue, the folder holds only `mocks/`.** Studio writes `product/ready/SLICE-NNN/mocks/<sha256>.<ext>` into its workspace when the slice is saved as an issue, and its answer (`mocks.folder`, `mocks.commit_as`, `mocks.note`) tells the product manager to commit that folder to the main branch, or hand it to an engineer. Studio never commits or pushes. No manifest is written there: the file names are the hashes, and the approval is the manifest, so nothing in the repository can widen what was approved.
3. **Intake holds the slice until they are there.** For an accepted slice issue with mocks, intake looks for each named picture under `product/ready/SLICE-NNN/mocks/` at the integration commit and checks its SHA-256 and its content. Until every one is there and matches, the slice is listed under `not_accepted` with `waiting: mocks` and a plain reason naming each missing or wrong file, never taken into the ledger and never built. The next intake (or pull) after the commit takes it in. Nothing about the issue changes in between, so its cached acceptance check is reused; only the files are read again.
4. **For a folder, the pictures are inside it.** `product/ready/SLICE-NNN/` holds `spec.md`, `why.md`, `slice.json` and `mocks/` with exactly the pictures `slice.json` lists; anything else is refused in plain words. `product import <folder>` takes `mocks/` the same way.

Why this arrangement: it keeps every existing check sound (the why and spec hashes still identify the text; the approval comment is still the one thing that says what was approved; the folder rule "exactly these files" still holds, extended to "and exactly the listed pictures"), it adds no Git or GitHub call (intake already reads `product/ready/` with `ls-tree` and `show`; Studio already writes the folder form), and a mocks-only folder is never mistaken for a ready folder (intake reads `mocks/` paths apart from the folder's three files).

## Checks on a picture

`issue_rules.image_facts(bytes)`, pure, standard library only, no image library:

- **PNG**: the eight-byte signature, `IHDR` first with length 13 (the size is read from it), every chunk's length inside the file, chunk types that are letters, and `IEND` last, ending exactly at the end of the file. CRCs are not checked.
- **JPEG**: starts `FF D8 FF`, ends `FF D9`; the segments are walked from the start to the first frame header (`SOF0` to `SOF15`, not `DHT`, `JPG` or `DAC`), which gives the size; image data or the end before any frame header is refused.
- **Bounds**: at most 5 MB (`MOCK_MAX_BYTES`), each side 1 to 10,000 pixels (`MOCK_MAX_SIDE`), at most four per slice (`MOCK_LIMIT`).
- **Against the approval**: `check_mock_file(item, bytes)` requires the SHA-256 and the format, width, height and length to be the approved ones.

Every reader calls them: Studio at `add` and again at `slice ready`, `slice mock list`, intake for an issue's files and a folder's files, `stored_mocks` before a cell is opened and when the cell is written. The verify station checks the cell's copy against the manifest's SHA-256 at `start` and every hash again at `finish`.

## Each choice

1. **Binding is an approved field of the mock, set with `--binding`, not a line in the spec.** The design says "`mock: binding` on the scenario"; the lead's brief says `--binding`. Recording it in the mock (which needs `--for`, so it is always bound to one scenario) puts it under the approval digest, keeps the spec grammar and its validator untouched while part A changes them, and keeps the spec free of pictures. Departure from the design's wording; the effect is the same: a difference fails the check only for a binding mock, on its scenario.
2. **The digest joins the approval, not the hashed text** (as the Jira key did). The why and spec hashes still identify the text everywhere they are used. A changed mock is a new revision: Studio's revision test compares the digest, and intake's revision digest (`digest_of`) includes it when there are mocks, so a changed set of pictures is a `modified` revision under the existing rules for revisions. Without mocks the revision digest is byte for byte the old one.
3. **`--for` must name a scenario the spec has now.** Checked at `add`, at `slice ready` and by `slice mock list`; a mock whose scenario was removed from the spec stops `slice ready` with "remove it and attach it again".
4. **The note** is one line, at most 200 characters, with no backtick, angle bracket or control character, so it cannot close a code span or a marker. It is the product manager's own words and is part of the approved list.
5. **One visible line per picture**, in a fixed form, after the Jira line and before `## Why`. `parse_slice_body` reads the lines back, and the body is "changed after it was approved" when they do not hash to the marker's digest. An approval for the same text with a different digest is refused as `mocks_changed`.
6. **`slice take` refuses a slice with mocks**: the pictures are not in the issue, so another product manager's workspace could not hold them. Said in plain words; nothing is changed.
7. **Intake's waiting state is a `not_accepted` item with `waiting: mocks`**, not a new list, so every existing report, `intake.refused` event (said once per distinct reason) and the run skill's wording already carry it. An earlier revision already in the ledger that waits behind it is marked unavailable with the same reason, as for any refusal.
8. **The cell's `mocks/`** sits beside `evidence/` in the cell folder (not in `repo/`), with `manifest.json` (`slice_id`, `revision`, `mocks_sha256`, and each mock with its `file`). It is replaced whole when a new revision is written into the cell (the builders' question answered), and absent for a slice without mocks. Cleanup archives it with the rest of the cell folder.
9. **Verification: each mock is also a check.** `compare` records the structured result (`results.json` `mock_records`) and a check `MOCK-N` (kind `design mock`) whose evidence is the copy in `evidence/mocks/` and the capture. That is what puts the mock beside the capture in the observer's evidence catalogue, which lists the files `results.json` records cite; `apps/` was not changed. The check's result is `fail` only for a binding mock that differs, so the existing verdict logic makes it `FAIL_WITH_EVIDENCE` with the differences in `findings.md`. Other outcomes pass the check and go to `summary.json` `mock_findings` for the product seat.
10. **The capture must be a picture from this run**: every rule of `record` applies (inside `evidence/`, captured after `start`, not the suite log or a station file, hashed), and at least one capture must start as a PNG or JPEG. `cannot compare` needs no capture, only a reason of a sentence. `differs` needs at least one difference in plain words; `--difference` is refused for any other result.
11. **`cannot compare` on a binding mock does not fail the check.** The design makes only `differs` a failure; a mock that cannot be compared is a finding the product seat judges, and it may block. Stated so a verifier cannot use it silently: it is listed in `mock_findings` and in the change record.
12. **The mock copy is never evidence**: `record` and `compare` refuse it as evidence, `capture` refuses to write into `evidence/mocks/`, and it never satisfies "screenshot". These refusals apply only when the cell has mocks, so a slice without mocks verifies exactly as before.
13. **Only `web`, `desktop` and `mobile`** compare. A cell of another app type with mocks verifies as before; its mocks stay in the cell.

## Not built

- **The visual app** (`apps/studio`, `web/`) neither shows nor attaches mocks; its host runs a fixed list of operations, which does not include `slice mock`. Showing the mock beside the capture in the Factory Floor's evidence player works through the existing catalogue (the mock and the capture are both cited by the `MOCK-N` check); no screen was added for it, and images still need `floor.evidence_media`.
- **Automatic image comparison.** The verifier looks and says what differs in plain words. No pixel or perceptual comparison is made.
- **`slice take` of a slice with mocks** is refused rather than supported.
- **Studio does not check that the pictures were committed.** `status` and `refresh` do not say a slice issue's mocks are still missing from the main branch; the Factory's intake says so.
- A picture committed to `product/ready/` is read whole before its size is checked (Git's `show`, as for the folder's text files); it is refused if it is over 5 MB.
- Release qualification does not name the mocks; the change record and the evidence do.
- No other picture formats (WebP, GIF, SVG); no limit on the total of a slice's pictures beyond four times 5 MB.

`tests/test_design_mocks.py` (21 tests), with tiny real PNG and JPEG files built in the test (`tests/mock_pictures.py`):

- the rules: PNG and JPEG accepted by content with their sizes; text renamed `.png`, a truncated PNG, trailing bytes, a JPEG without its end and a signature with no chunks refused; 20,000 pixels and over 5 MB refused; a slice without mocks renders and parses exactly as before; the marker, the visible lines, the note and the approval with mocks; an edited line, note or scenario makes the body changed; the list's form (empty, duplicate, binding without a scenario, a matrix rule as scenario, a backtick in the note, another format, an unknown field, five pictures);
- Studio: `add` refuses a renamed text file, an oversized picture, an unknown scenario and `--binding` without `--for`; stores the picture and the work order, refuses a repeat and a fifth; `list`; `remove` deletes the file; nothing calls GitHub; marking ready on GitHub binds the digest in the body and the approval, writes the pictures to commit, and says so; a changed mock needs reopening and is revision 2, and removing the last mock leaves the body and the workspace as without mocks; a slice without mocks answers as before; the ready folder carries the pictures and lists them; `slice take` refuses a slice with mocks;
- intake on the stand-in GitHub and a shared bare repository: an issue waits with the plain reason until the product manager commits what Studio wrote, then is taken in, kept in `received/`, dispatched, and the cell has `mocks/`, `manifest.json` and `product.mocks`; a committed picture with the wrong hash, then a text file under the right name, keeps it waiting; mocks changed on GitHub after approval are `mocks_changed`; a folder carries its pictures and a wrong one is refused; a folder with an unlisted picture is refused; a slice without mocks reaches the ledger and the cell with no `mocks` key and no `mocks/` folder;
- verify: `start` lists `MOCK-1` and copies it; `finish` is incomplete without a side-by-side record; `compare` refuses a capture that is not a picture, the mock itself as capture or as evidence, and `differs` without a difference; a match passes and the summary carries the result, the `MOCK-1` check cites the mock and the capture, and the mock never counts as a screenshot; a binding mock that differs is `FAIL_WITH_EVIDENCE` with the difference in `findings.md`; a non-binding difference and a `cannot compare` pass with two `mock_findings`; a changed picture in the cell stops `start`; a `library` cell with mocks verifies as before;
- the change record's lines for a mock with a difference and one with an unreadable hash.

The whole suite was run with these changes (`make test`): 1541 tests in 341 classes, OK (1 skipped). Not tried against GitHub itself, a real browser capture, or the Factory Floor.
