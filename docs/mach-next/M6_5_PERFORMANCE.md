# M6.5 Factory Analytics: performance

Measured on 2026-11-14 with `web/apps/control-tower/scripts/analytics-measure.mjs` (how to run it, what each
step does and the budgets' origin: `M6_5_TESTING.md`). Three runs on the realistic large project, each
against the M6.3 observer (`b37c036`) on an identical copy of the same project. Every figure below is the
median of the three runs, with the range in brackets where it matters.

## 1. Method

- **Project**: `mach-synth --analytics --profile realistic --cells 330 --waves 40 --events 240000 --seed 1`
  (327 finished tickets, 712 executions, 5 Oct to 1 Nov 2026), generated by the harness into its scratch
  folder. Each run appends 3,000 events (`mach-synth --append`, 200 a second for 15 s), so the three runs
  started at 246,270, 249,270 and 252,270 events. Both binaries ingest the project with 0 refused records.
  The generator was corrected afterwards so that the 4 outcome-unknown executions carry no `result.json`
  (they read as outcome unknown, not interrupted); the measured copy predates that. Four records out of
  about 250,000 do not change the costs measured here; a re-run would regenerate the project.
- **Binaries**: the working tree's `mach-observer` (`go build`, commit `de1ec9b` plus uncommitted work of
  that afternoon) and `b37c036` built from `git archive b37c036 apps/observer` with `go build`.
- **Per run, per binary**, in this order: delete the index and start (cold rebuild, until caught up);
  stop and start again (restart from the saved projection); every query cold once, then 5 times warm and
  5 times with `at=<head cursor>`; a comparison (two filtered metrics queries at one cursor, together, 5
  times); 15 s settle, then 20 s idle (CPU time from `ps`, the largest RSS); 15 s of appended events
  (CPU time, CPU per appended event, a query every 250 ms) and the time to catch up afterwards. The
  working tree's run then measures the UI in headless Chromium at 1512x982: navigation to the first
  figure (5 loads), area switch (3 rounds of 7 areas), window preset (9), filter (9), switch to Compare
  (3), brush drag release (4), hover to tip (15 marks), JS heap after GC before and after all of it. UI
  times run from the action, in the page, to the last DOM change it caused.
- **Quiet machine**: no other agent was running. Before each run the harness waited, polling once a
  minute, until the 1-minute load average was under 2.0 (it settled within 3 minutes each time).

## 4. Against the baseline

| Measure | b37c036 | Working tree | Change |
|---|---|---|---|
| Idle CPU | 3.0 % | 27.7 % | about 9x; the only change large enough to notice without measuring (a quarter of a core while nothing happens) |
| CPU per appended event | 3.0 ms | 7.3 ms | 2.4x (144 % of a core at 200 events a second, against 60 %) |
| Restart from the saved projection | 6.7 s | 12.5 s | 1.9x, now over the 10 s budget |
| Cold rebuild | 26.0 s | 32.9 s | +27 %, within budget |
| Idle RSS | 270 MB | 317 MB | +17 %, within budget |
| Warm query, like for like ("metrics, all") | 0.6 ms | 9.4 ms | 16x, from far below to within budget; the response is richer |
| `runs` warm | 0.5 ms | 16.7 ms | 33x, within budget |
| Catch-up after appending | 19 ms | 14 ms | no regression |

Every UI budget passes, and every query budget passes. Three observer budgets fail for the working tree:
idle CPU, CPU per appended event, and restart. Idle CPU and CPU per appended event are also over budget at
`b37c036`, so those two budgets (2 % and 1 ms, proposed before any baseline was measured) were tighter
than M6.3 itself; the regressions against M6.3 are the ratios above. Restart is a new failure.

## 5. Not measured, and limits

- The UI has nothing to compare against at `b37c036` (Analytics did not exist).
- The cause of the idle CPU and per-event cost was not profiled. The engine agent's note: metric folds run
  only when an event is applied, so idle cost is more likely the ingest polling loop or the timeline cache;
  a CPU profile of an idle observer and one under `--append`, against `b37c036`, would settle it.
- One machine, three runs; the ranges are narrow for CPU and rebuild, wider for the UI's Compare switch
  and the baseline's per-event CPU.
- Raw reports (JSON, per run): `analytics-measure-live.json` in the harness's `--out` folders; not kept in
  the repository.
