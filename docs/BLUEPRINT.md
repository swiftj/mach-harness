# MACH (Multi-Agent Construction Harness): the factory blueprint

This is the reference for what MACH does. The short guide for working on this repository is `CLAUDE.md` at its root.

## 1. Project Overview & Vision

**MACH** (**M**ulti-**A**gent **C**onstruction **H**arness) is an enterprise-grade, end-to-end agentic software factory built exclusively on **Claude Code** and **Claude Dynamic Workflows**.

MACH shifts software engineering from manual pair-programming and prompt-based "vibe coding" to an architecturally enforced, autonomous manufacturing pipeline. It ingests sliced PRDs, technical specs, legacy architectures, or live production crash telemetry, orchestrates specialized sub-agent personas through isolated development cells, verifies functionality using multi-target deterministic evidence, and delivers tested, verified, production-grade applications.

### Core Architecture Principles:
1. **Pure Claude Control Plane**: Replaces external proxy daemons and rigid waterfall state machines with native Claude Code orchestration. The orchestrator dynamically assigns model tiers and reasoning effort parameters directly within workflow definitions.
2. **Cellular Von Neumann Isolation**: All construction occurs within ephemeral Git worktrees (`.factory/worktrees/<ticket_id>/`) or cloud sandboxes. Sub-agents never touch `main` directly and are terminated upon task completion, eliminating context rot and file overwrite collisions.
3. **Strict Artifact Chain**: Every task progresses through an immutable specification pipeline:
   `Telemetry / Ticket` ──► `intent.md` (Why) ──► `spec.md` (What) ──► `Typed Contracts` (.proto) ──► `plan.md` (How).
4. **Multi-Target Dynamic Evidence**: Rejects speculative self-reporting. Code must be objectively proven via target-appropriate evidence: Playwright browser recordings (Web), VHS terminal GIFs (CLI), gRPC benchmark graphs (Backend), OS frame grabs (Desktop/Mobile), or test flamegraphs (Libraries).
5. **Multi-Agent Consensus & Capped Review Loops**: Independent reviewer panels with fresh context windows conduct multi-pass code reviews. Reviews are strictly capped at 3 loops before escalating blocked work to human SMEs.
6. **Continuous Self-Improvement**: Production observability (Sentry, PostHog, Datadog) triggers automated self-healing tickets, while observer agents continuously mine review logs to submit auto-tuning PRs for factory rules and skills.

## 2. Model tiers

MACH maps its sub-agent roles to four tiers. Which model each tier uses is set in `.factory/config.json` under `models`; the names below are tiers, not models.

```
┌──────────────────────────────────────────────────────────────────────────────────┐
│                             MACH MODEL ASSIGNMENT TIER                           │
└──────────────────────────────────────────────────────────────────────────────────┘
  1. PLANNING & GROOMING ──► 2. CONTRACT ENGINEERING ──► 3. TDD BUILD & QA VERIFY ──► 4. UTILITY & CLI
     planning                   contracts                 build                      utility
  (long-horizon)               (deep spec and reasoning) (balanced workhorse)       (fast, low cost)
```

| Model Tier | Assigned Sub-Agent Personas | Target Skills | Role & Core Responsibilities |
| :--- | :--- | :--- | :--- |
| **planning** | Lead Architect, Strategist, Meta-Observer | `/mach-intent`, `/mach-observe` | Long-horizon planning, multi-PRD decomposition, enterprise constraint alignment, and meta-learning analysis across execution logs. |
| **contracts** | Staff Systems Engineer, Senior Reviewer | `/mach-intent`, `/mach-review` | Deep technical reasoning, Protocol Buffer contract design, architectural specification, and high-risk scrutiny evaluation (auth, billing, DB migrations). |
| **build** | Software Engineer, Evidence QA Engineer | `/mach-build`, `/mach-verify`, `/mach-audit` | Daily development workhorse. Writes failing unit tests first (TDD), implements clean service-layer code, executes multi-target verification runners, and performs repo audits. |
| **utility** | Triage Assistant, Operations & Janitor | `/mach-ticket`, `/mach-cleanup` | High-volume, low-cost utility engine. Executes local ticket CLI operations, normalizes JSON payloads, formats code, prunes worktree cells, and archives logs. |

The cell folder holds the factory's artifacts; `repo/` inside it is the isolated checkout. Keeping them apart means artifacts never pollute the project's tree and need no git exclusions. A project with no git history yet has no `repo/`; the cell then works in the project root until the first commit.

**A cell holds no Claude Code configuration.** Claude Code's sandbox refuses writes to `.claude/` and `.mcp.json` in the working directory and the folders above it, and no allow rule lifts that, so a full checkout of a ticket's branch could not be made or kept up to date there. `repo/` is therefore a sparse worktree (`skills/intent/scripts/workspace.py`, shared by `cell.py open`, `build.py start` and the doctor): `git worktree add --no-checkout`, then `git sparse-checkout set --no-cone '/*' '!.claude/' '!.mcp.json'` and `git reset --hard HEAD` in it. Every `.claude/` folder and every `.mcp.json`, at any depth, is left out for the life of the cell. The patterns live in that worktree's own configuration (`extensions.worktreeConfig`, which Git turns on for the repository); the main checkout stays a full checkout. The branch still carries the files, so commits, merges of main (a MACH update included), the pull request and landing carry them unchanged, and Git never writes them into the cell; `git status` and diffs do not show them as deleted. It needs Git 2.36 or later. Skills, agents and the belt workflow are read from the project root, never from a cell, so no station needs those files there. A cell made before this keeps its full checkout. In a Git repository with at least one commit, a workspace that cannot be made stops the ticket with what Git said and what to do, and removes the branch, folder and worktree record it made; the ticket never works in the project root instead. A plan task, touch map row or contract under `.claude/` or naming `.mcp.json` is refused by `check-plan`: a person makes that change outside the factory. Prose that mentions such a path is not refused.

**Installing and updating (`bin/mach`).** MACH's scripts import each other across skills, so a project must hold MACH's files from one version only. Install and update therefore always bring MACH's own files to the version being installed: everything under `.claude/skills/mach/`, `.claude/skills/mach-*/`, `.claude/agents/mach-*` and `.claude/workflows/mach-*`, and `.factory/bin/mach`, `.factory/mach.mk` and the two programs in `.factory/bin/`. A file there that was changed after it was installed, or that the manifest does not list, is copied to `.factory/mach-backup-<time>/` and then replaced (`replace  <path> (your version saved to <backup>)`), with no `--force`; a changed one this version no longer ships is backed up and removed. The output ends with how many were replaced and where the saved copies are, and the install exits 0. Seeds (`.factory/config.json`, `REVIEW.md`, `AGENTS.md`, a new `Makefile`) are created only when absent and never overwritten. Any other file the installer would write is never overwritten when it did not install it or it was changed since, unless `--force`, which backs it up first. `mach status` and `/mach doctor` (`install.files`) say when MACH's files do not match the manifest for the installed version (changed, missing, or, for `status`, in MACH's skill folders but not in the manifest), and that running the installer again fixes it. In a script install, Product Studio (`studio.py`) reports an `AttributeError` or `ImportError` raised for one of MACH's own modules as "MACH's files in this project are from different versions; run the installer again." Uninstall still keeps a changed file unless `--force`.

## 4. The Complete MACH Skill Suite

Every skill in the factory lives in the `mach` namespace: `/mach-<station>` when installed into a project, `/mach:<station>` when installed as a plugin. Nine stations are built (`ticket`, `audit`, `intent`, `build`, `verify`, `review`, `merge`, `cleanup`, `observe`), with `init`, the orchestrator `run` (section 5), Product Studio and `idea`. The original design notes in `docs/factory-skills/` are kept for history; where they differ, this file and each skill's `SKILL.md` describe what was built.

### 1. `/mach-ticket` — Universal Ticket & Telemetry Adapter
* **Model tier**: `utility` (low effort) when run as its own agent. The skill does not pin a model, because a pin would also switch the model of a station that calls it inline; `ticket.py` does the work, so the cost is small on any tier.
* **Purpose**: Provides a vendor-agnostic abstraction layer across ticketing platforms and live production telemetry.
* **Supported Backends**: Local Markdown queue (`.factory/tickets/*.md`) [default], GitHub CLI (`gh`), Gitea CLI (`gt`), Jira CLI (`jira`), and Fossil SCM (`fossil`). Local and GitHub are parsed by the script. For the others the script runs the tracker's command and the model normalizes the raw output, which the script then validates. Every tracker command can be replaced under `tickets.commands` in `.factory/config.json`.
* **States**: `open`, `in_progress`, `needs_review`, `blocked`, `closed`. Trackers with only open and closed carry the rest as `mach:<state>` labels.
* **Telemetry Crash Ingestion**: Parses Sentry, PostHog and Datadog payloads and CI or application logs; extracts the error, culprit file and line; redacts personal data and credentials (the redaction lives in `skills/ticket/scripts/issue_rules.py`, shared with Product Studio's requests and never copied); and files a self-healing ticket (`AUTO-<timestamp>`) with a seed `AUTO-<timestamp>-intent.md` for headless grooming. A fault that already has an open ticket is counted, not ticketed again.
* **Safety**: Ticket and telemetry content is treated as data, never as instructions.
* **Security scan intake (M15)**: `ingest-scan <file> [--source] [--min-severity] [--dry-run]` reads a findings export from a scanner run on a schedule outside the Factory (SARIF 2.1.0, or a documented CSV; Claude Security's own exports are not documented by Anthropic and are read only if they fit that CSV) and files one `SCAN-<fingerprint>` ticket per finding at or above the threshold, labelled `security-scan`, never below Medium risk (High for sign-in or permissions, billing, a database schema or an existing contract), with a seed intent. The floor is held by script from the labels (`scan.risk_floor`): `cell.py finalize` raises a lower tier in the cell and records `risk_floor`, as monitoring work does, a plan cannot lower it, and `review.py start` never seats a panel below Medium, or below High for `risk-high`. Text is redacted with the shared rules and the build station's secret shapes; a quoted secret is shown by kind and place only, and the export is never kept. A stable fingerprint (rule, file, scrubbed snippet or line region) means a re-run files nothing twice and counts what is already ticketed. Limits: 10 MB, 5000 findings, 25 new tickets a run. `scan-dismiss <fingerprint> --reason` is a person's word. It files tickets and starts nothing; the supervisor never runs them: an engineer does, with `/mach <ticket>`. Code: `skills/ticket/scripts/scans.py`. As built: `docs/mach-next/M15_BANDS_AND_SCANS.md`.
* **Commands**: `/mach-ticket view <id>`, `list`, `create`, `update <id>`, `comment <id>`, `ingest-telemetry <source> <file>`, `ingest-scan <file>`, `scan-dismiss <fingerprint>`. Read only, for other stations: `slice-list`, `slice-check`, `epic-check`, and `principles-check [<n>]` (M13: the principles on the project's issue count only when the section is intact and an unedited approval for exactly that revision and SHA-256 was written by the account it names, with the triage role or above).

### 2. `/mach-audit` — Repository Readiness Scorecard & Pre-Flight Gating
* **Model tier**: `build` (medium effort) when run as its own agent; the skill does not pin a model. `audit.py` measures and scores; the model only explains the result and finds commands the script could not detect.
* **Purpose**: Audits repository health across 5 pillars, 100 points in all, before autonomous agents are permitted to touch code:
  1. Reproducible Environment & Build (25): build definition, locked dependencies, a one-command build that runs cleanly.
  2. Baseline Test Suite (25): tests exist, one command runs them, 100% green, under 5 minutes.
  3. Linting, Formatting & Static Analysis (20): linter configured and passing, formatter, type checking, secret scanning.
  4. Rules & Boundary Contracts (15): `CLAUDE.md`, `AGENTS.md`, `REVIEW.md`, a real README, typed contract files.
  5. Repository Hygiene (15): git history, clean working tree, `.gitignore`, no conflict markers, protected main branch.
* **Gating Tiers**:
  * **Gold (90–100%)**: Full autonomous execution permitted.
  * **Silver (70–89%)**: Autonomous build permitted with mandatory human review before PR merge.
  * **Bronze/Fail (<70%)**: Autonomous execution blocked; hardening work is filed as a `repo-hardening` ticket.
* **Blockers**: A build or test suite that fails, is missing, or could not be run makes the tier Bronze whatever the score. Checks that cannot be verified locally are reported as unverified, never assumed to pass.
* **Notes**: a project whose required ADR topics (`adr.required_topics`) are not all covered gets a note naming them, and ADR files that cannot be read get one too. The hold is at planning, not here. A note changes neither the score nor the tier.
* **Gate**: `audit.py gate` is what other stations call. It refuses when the report is missing, older than `audit.max_age_days`, for a different commit than the main checkout, or Bronze.
* **Output**: `.factory/audit-report.json`. Options: `--strict` (Gold or fail), `--fix` (create a missing `.gitignore`), `--json`.

### 3. `/mach-intent` — Socratic Grooming, Slice Spec, Contracts & Plan
* **Model tier**: the interview on `planning` (or the session's model); stage 2 on `contracts` via the `contract-engineer` agent
* **Purpose**: Turns one ticket into the artifact chain.
* **Stage 1 — Interview**: Carves the ticket down to one thin vertical slice (the skill decides scope, deferring the rest to reserved slice IDs) and interviews the product owner **one yes-or-no question at a time, each with a recommended answer**, until every branch of the design tree is settled. Facts are looked up by sub-agents, never asked. Writes `intent.md` and a business-level slice spec: RFC 2119 invariants, EARS functional requirements, a complete decision matrix, and Given/When/Then scenarios. No status codes, schemas or technology appear in the spec.
* **Deterministic gates**: `validate_slice.py` checks structure, grammar, matrix completeness and traceability; `cell.py finalize` requires zero open questions before it exports `spec.json`.
* **One slice ID space**: `cell.py next-id` allocates over the main checkout's `specs/slices/`, every open cell, Product Studio's draft workspace and the product work orders, and (M20) the specs on `origin/<main>` as last fetched (it fetches nothing) and, when the ticket provider is GitHub, every slice issue's ID, open or closed (`ticket.py slice-ids`); when GitHub cannot be read it says so in `not_counted`. Two engineers numbering in the same minute can still take one number: the merge station refuses the second (section 5), and `validate` and `finalize` refuse a spec whose ID another spec in those folders already uses (`duplicate-slice-id`). A slice Product Studio handed over is one slice on both sides of the hand-off, whatever its file is named on each side (Studio keeps the name the draft was started with; intake names it from the spec's title), and each side knows it from its own record, never from the text: a cell's `product.slice_id` (on intake's first `finalize`, before the cell records it, `--from-studio SLICE-NNN`) means the Studio draft with that ID is not another slice; Studio's `issues.json` (marked ready, saved to the folder, or taken from GitHub, reopened since or not) means the Factory's copy with that ID, in a cell or on the main checkout, is not another slice. Any other file with the same ID is still a duplicate.
* **Effects on shipped behaviour (M13 B)**: every spec has `## Effects on shipped behaviour`: `None.` or one row per shipped rule it touches (`SLICE-NNN/FR-NN` `kept` with a scenario proving it on this slice's data, `changed` or `replaced` with the rule taking its place, `retired` with the product manager's reason). `skills/intent/scripts/shipped.py` reads the shipped rules from the integration branch's local Git objects (the current-behaviour view, loaded by path); `cell.py validate` and `finalize` pass them to the validator (`--shipped`), which then requires the section and refuses a row naming a rule that never shipped or is no longer in force; `finalize` records the commit checked against in `cell.json` `shipped`, and `cell.py status <ticket>` flags a row whose rule has since been replaced or retired. `cell.py shipped` prints the rules in force, fenced as data, for the interview: each rule the slice touches is one question, and in headless mode a rule changed, replaced or retired is an open question. The contract engineer lists the earlier slice's tests that name a changed rule as files to change. As built: `docs/mach-next/M13_EFFECTS.md`.
* **Product principles (M13)**: when the project has principles, the spec answers every active one in `## Principles` (after Acceptance criteria): its ID and revision, its statement quoted exactly, and `Applies` (the INV, FR or AC IDs that uphold it), `Does not apply` (one sentence why) or `Exception` (the product manager's reason; never recommended). `validate_slice.py --principles <file>` refuses an unanswered principle, a wrong quote or revision, an unknown principle, and an `Applies` naming an ID the spec lacks; without the file each row is checked on its own, and a project with no principles needs no section. The interview reads them first, follows them in recommendations and makes a conflict the next question; headless, a conflict is an open question. On an engineer's ticket `cell.py principles <ticket>` reads the published ones (the project's issue through `ticket.py principles-check`, else `product/ready/PRINCIPLES/` committed on the main checkout), checks them and keeps them in the cell for `validate` and `finalize`; none readable means no section, said once. With more than one open project issue (`principles-check` lists them in `project_issues`), grooming stops instead: `cell.py principles` refuses with one sentence naming the issues and saying a person closes the one that should not be there, and `validate` and `finalize` refuse the same until it is run again (M20). As built: `docs/mach-next/M13_PRINCIPLES.md`. Slice IDs are allocated across every open cell so parallel tickets cannot collide.
* **Stage 2 — Contracts & plan**: A fresh-context contract engineer works from `spec.json` alone to write the boundary contracts and a test-first `plan.md`. `cell.py check-plan` requires every requirement and scenario to be assigned to a task, tests before implementation, and each listed contract to exist. It refuses a plan whose tasks, touch map or contracts change a file under `.claude/` or a `.mcp.json`, which a cell never holds: a person makes that change outside the factory. Changing a contract that already exists on the main checkout raises the ticket to High risk, and `cell.py check-plan` enforces it; adding a new contract does not. The plan names under `ADRs` every architecture decision it relies on or proposes, and `check-plan` holds it to the accepted ones (see **Architecture decisions** in section 5). A spec corrected after its plan was written (a defect the contract engineer found, settled by the product owner's answer) needs no separate instruction to plan again: `cell.py finalize` sees that the spec changed, keeps the old plan in the cell's `plan-history/` and returns the cell to `spec-ready`. Nothing is built yet, so nothing is lost. `cell.py replan` remains for a plan a person says is wrong, and for a cell already being built. A slice handed over by Product Studio is never patched in the cell: a defect only the product manager can settle is recorded with `cell.py spec-question <ticket> --question "..."`, the ticket stops (`product-answer`), the Factory puts the question on the slice's issue, and the product manager's new revision is taken into the cell and planned again.
* **Modes**:
  * *Interactive*: the default.
  * *Headless* (`--headless`, which the orchestrator passes for `AUTO-` tickets): answers each question from facts or safe, strict defaults and records every one as "Decided without a PM"; anything touching money, access, irreversible deletion, or conflicting rules becomes an open question, which blocks stage 2 and labels the ticket `blocked-requires-sme`.
* **Policy packs (M14)**: `policies/<pack>/policy.md` (an owner, `status`, `applies-to` in the ADR grammar, statements `POL-<pack>-NN`), read from the main checkout's committed state by one helper, `skills/intent/scripts/policies.py`; a malformed pack is a problem, never skipped. The interview reads the active packs first (`cell.py policies`, Studio's `slice resume`) and makes a conflict the next question. The spec's optional `## Policies` (after `## Principles`) answers each pack that applies (`all`, or a `topic:` the spec names) with its digest and `Followed.` or concerns; a concern names the statement, why, the owner, and `open`, `spec changed` or the owner's acceptance. The validator is given the packs (`--policies`) and stays pure; rows reach `spec.json` as `policies`. An open concern stops `slice ready` and leaves `cell.py finalize` at `spec-open`; only `policy accept` (Studio, or `cell.py policy-accept` for a ticket groomed here; `/mach policy accept`) records the owner's words, on a person's explicit word, never headless or in a supervised execution. A Product Studio slice is checked at `slice ready`, not again at dispatch. `finalize` keeps each answered pack's text in the cell (`policies/`, `cell.json` `policies`); `check-plan` refuses a task that changes a pack; `cell.py status` flags a pack changed since (`policies_changed`), never restarting. Starter pack: `templates/policies/security/`, not installed. As built: `docs/mach-next/M14_POLICY_PACKS.md`. Since M15 an owner may name GitHub logins (`Role (@dana, @lee)`); `policy accept --by` must then be one of them (any case, with or without `@`) or in `policies.accept_by`, else it is refused; a team- or role-only owner is recorded "not checked against the owner". The check is written in brackets after the name in the resolution line, so reviewers read it wherever the name is shown; it guards against accident, not forgery, and never asks GitHub. The acceptance of the last open concern lifts the `policy-owner` hold. As built: `docs/mach-next/M15_LOOSE_ENDS.md`.
* **What counts as small (M18 part A)**: `skills/intent/scripts/small.py`, loaded by Product Studio, by this station and by intake, never copied, answers `small` or `not small` with one fixed sentence naming the rule that decided; the first rule that does not hold, in a fixed order, decides, and nothing takes an override. From the validator's model: one actor (the validator's single-actor test, decisive here) and at most one epic; at most `requirements` functional requirements, `scenarios` scenarios and one decision matrix table; at most `changed_shipped_rules` effects rows `changed` or `replaced`, none `retired`; no principle answered `Exception`; no pack answered `Concerns`, whatever the resolution; `Required permissions` beginning with "None"; every slice depended on, and every `SLICE-NNN` named under `External dependencies`, shipped; no risk tier given High. Missing data is never evidence. From the plan (`judge_plan`, at `check-plan`): no existing contract changed, no file `scans.py` `risk_for` rates High, no ADR proposed. The limits are `intent.small_change` in `.factory/config.json` (3, 4, 5 questions, 1; the last can only be lowered); an unusable value reads as its default, with a note. The short interview is `references/small-change.md` (fix or adjustment; look up, propose the whole spec, at most `questions` yes-or-no questions, confirm; leaving the light path in one fixed sentence, never trimming). As built: `docs/mach-next/M18_ENGINE_A.md`.
* **A small change in the cell (M18)**: an engineer's own ticket takes the short interview on their word (`cell.py open <ticket> --small`; the run skill adds `--small` to the intent skill's input when the person said so) or on the ticket's `small-change` label; headless grooming and `AUTO-` tickets never do, and `--small` with them is refused. A slice from Product Studio brings its kind with it (intake writes it before finalize). `cell.json` then carries `kind: small`, `small: {from: engineer | label | product-studio, and from Studio change and shipped_rule}`, and, once it left the light path, `widened: {at, reason, rule, by}`; `spec.json` carries `kind` and `widened`; every other cell and spec is exactly as before. `validate` and `finalize` judge a ticket still on the light path (`small.judge`: intent.md's tier and the risk floor the cell holds, a Studio slice's epic and dependencies, the shipped slices on the integration branch) and widen one a rule says is not small, with the rule's sentence: never refused for its size, never trimmed. A `finalize` that widens it saves it at `spec-open` (`WIDENED`), not ready, so the interview carries on in full first. `cell.py widen <ticket> --by-rule <rule> | --why "<words>"` does the same while the spec is written. `check-plan`, on a valid plan, applies `small.judge_plan` (an existing contract changed, a file `risk_for` rates High, a proposed ADR) and treats a plan raised to High as the `risk` rule: an engineer's own ticket is widened and goes back to `spec-open` with its plan kept in `plan-history/` (`WIDENED`, nothing built); a Product Studio slice, whose spec is the product manager's, stops with their question on its issue through `spec_question` (`STOPPED`, `needs: product-answer`), a fixed sentence quoting the rule's, and comes back as a new revision. The same stop holds at `finalize` for a Studio slice the Factory judges not small. As built: `docs/mach-next/M18_ENGINE_B.md`.
* **Outputs**: `intent.md`, `spec.md`, `spec.json`, `plan.md` and `cell.json` in the cell; the slice spec and contracts committed on `feature/<ticket_id>`.

### 4. `/mach-build` — TDD Builder & Design-System Anti-Slop Anchor
* **Model tier**: `build` (high effort), pinned in the `builder` agent
* **Purpose**: Executes construction inside the isolated Git worktree cell using strict Test-Driven Development (TDD), following `plan.md` task by task. The model writes tests and code; `build.py` runs the tests, decides whether each step counts, and makes every commit.
* **Start gates**: the audit allows building (a Bronze repository builds only `repo-hardening` tickets); the cell is `planned` and its spec unchanged; the cell is isolated and clean; the tests pass before anything is touched.
* **Builds on today's main (M13)**: `start` and `revise`, and no other step, bring the branch up to date with the main checkout's committed HEAD: already up to date, nothing happens; a clean merge is one merge commit by the station, recorded in `build.json` and the build report (`main_merges`: the main commit, when, how many commits behind), and the tests then run on the result (a failure only once main is merged in is said in plain words); a conflict, or a merge that would change the slice spec, is aborted and changes nothing, and a conflict is recorded in `cell.json` (`main_conflict`) so `run.py next` stops with `needs: main-conflict` until a person commits the merge in the cell or main moves on. The merge is not a task: scope, frozen tests and the secrets scan judge only what the builder changes after it, and the report's files and diff leave out what main brought. `build.update_from_main: false` switches it off. As built: `docs/mach-next/M13_BUILD_ON_MAIN.md`.
* **Enforced by script**:
  * **Order**: tasks are completed in plan order, each with the step its kind requires.
  * **Red before green**: a `[test]` task is accepted only if the suite fails with it; an `[impl]` task only if the whole suite passes. To see a new test fail, the station runs only the new test files where it has checked, at the start, that a committed test file passes when run on its own in this project (`build.commands.test_file`, or worked out for unittest and pytest); otherwise, and whenever the new test passes on its own, it runs the whole suite as before. Where one test can be run on its own (unittest and pytest, checked the same way), the task's own tests, the ones it added or changed, are each run alone: a test that already passes before any code is written is never counted as seen failing because other tests in the same file or suite fail, and needs the `--covered` reason, which is recorded with its name. Code tasks always run the whole suite, and so does the finish, unless the last task's whole-suite run passed on exactly the commit that is the branch's tip, in which case that run stands and is not repeated.
  * **Frozen tests**: a committed test cannot be changed by a later non-test task.
  * **Scope**: a task may change only the files the plan gave it.
  * **Traceability**: every `FR`, `INV` and `AC` in the spec must be named by a test before the build can finish. A `[test]` task that leaves out or respells an ID the plan gave it (`fr02` for `FR-02`) is refused when the test is written, while it can still be edited.
  * **Overrides are recorded**: each gate has an override that requires a reason, and every use is written to `build-report.json` for the reviewers.
  * **No secret enters the branch (M12)**: before each commit the station makes (task steps and revisions), the added lines of what is about to be committed are scanned by `skills/intent/scripts/scan.py` for credentials by their well-known shapes (private key headers, AWS, GitHub, Slack, Stripe live, Google API keys, JWTs, `sk-` style keys, a password in a URL, and a long high-entropy string assigned to a name like `secret`, `token`, `password` or `api_key`). A candidate refuses the step with file, line and kind. The override is `--not-a-secret "<why>"`, recorded in `build-report.json` (`deviations` and `secret_scan`) with the places it covered, never the value; the builder's instructions forbid it for a real credential.
  * **Architecture decisions**: the builder is given the accepted ADRs the plan was made under and has no override for them; no task changes a file in the ADR folder, and a High-risk ticket whose plan proposes an ADR does not start until a person accepts it. The build report lists the ADRs in force and every exception.
* **Design System & Anti-Slop UI Anchor**: For frontend work the builder finds the existing component library and design tokens first and must reuse them, with semantic HTML and ARIA accessibility. Inline styles and hard-coded colors added in interface files are listed in the build report.
* **No Dead Code**: Prohibits unused helpers, spurious dependencies, and monolithic multi-thousand-line files.
* **Revision rounds**: `build.py revise` starts a revision after a failed verification or a rejected review. A ticket gets three judging rounds in all; on the third failure it refuses and directs escalation to `blocked-requires-sme`.
* **Output**: commits on `feature/<ticket_id>`, one per task; `build.json` and `build-report.json` in the cell; cell stage `built`. The report's `timing` says where the time went: each step's test run and whether it was the new tests only or the whole suite, the time since the previous step, and totals. Test time is measured; elapsed time is the clock and includes idle time.

### 5. `/mach-verify` — Multi-Target Dynamic Evidence Engine
* **Model tier**: `build` (medium effort, fresh context), pinned in the `verifier` agent
* **Purpose**: Independent, objective verification. The verifier runs the built slice the way its user would and captures what happens; `verify.py` decides whether verification may start, what must be proven, whether each claim has real evidence behind it, and the verdict.
* **What must be proven**: every scenario (`AC-NN`) with the scenario's own data; every decision matrix rule (`RN`) with data the verifier invents, which serves as a holdout the builder never saw; and any check a person left in `.factory/holdouts/<ticket_id>/`.
* **Neighbouring shipped scenarios (M15)**: at `start`, `neighbours.py` picks up to `verify.neighbours` (default 2, 0 off) scenarios that shipped with other slices of the same epic, by rule: never from a slice whose rule this spec changes, replaces or retires, never one covering a kept rule or a rule no longer in force; the slices it depends on first, then the most recently shipped (slice ID order), one per slice before a second. Each is a required `NEIGHBOUR-N` with its Given/When/Then from the shipped spec at the integration commit. A failing one is a failed check ("a shipped scenario of SLICE-NNN no longer holds") and goes back to the build station; the findings say the change broke shipped behaviour or the spec should have declared an effect (the product manager's call, reached through `/mach replan` and `cell.py spec-question`). The choice is in `results.json`, `summary.json`, the review packet (product seat) and the change record. No epic, nothing shipped, no Git or no helper: none, said once. As built: `docs/mach-next/M15_VERIFY_REVIEW.md`.
* **Evidence by target** (required kinds are enforced per `app_type`):
  * **Web Apps (`web`)**: Playwright/Cypress runs, capturing PNG screenshots and WebM video recordings or traces.
  * **CLI & Terminal Tools (`cli`)**: VHS/Asciinema terminal recordings or transcripts, and an `exit-codes.json` log.
  * **Backend APIs (`api` / `grpc` / `rest`)**: `curl`/`grpcurl` request and response dumps, contract comparison, and database state diffs.
  * **Desktop & Mobile Apps (`desktop` / `mobile`)**: OS automation (`cliclick`, `xdotool`, Android ADB, iOS Simulator) capturing window frames and interaction recordings.
  * **Libraries & SDKs (`library`)**: a consumer-side driver transcript and a public API surface comparison.
* **Enforced by script**: only an unchanged, built cell can be verified; the suite is rerun and contract files checked automatically; each record needs an evidence file captured in this run, inside `evidence/`, hashed so later edits are caught; the builder's own test log cannot stand as evidence; the verifier may not change the cell's code.
* **Design mocks (M14 C)**: for a `web`, `desktop` or `mobile` cell with design mocks, `start` checks each picture in the cell's `mocks/` against its hash, copies it to `evidence/mocks/` and lists it (`MOCK-N`); `verify.py compare <ticket> MOCK-N --result matches|differs|cannot-compare` records one side-by-side result per mock, citing a picture of the built screen captured in this run (`differs` lists each difference in plain words, `cannot-compare` gives the reason). Each is also a check citing the mock and the capture, so the two are catalogued side by side. A `differs` on a binding mock fails the check; any other `differs` and every `cannot compare` go to the product seat as `mock_findings`. A mock copy is never evidence and never counts as a screenshot. As built: `docs/mach-next/M14_DESIGN_MOCKS.md`.
* **Verdicts**: `PASS` (stage `verified`, ready for review); `FAIL_WITH_EVIDENCE` (writes `findings.md` and returns to the build station, using one review loop); `INCOMPLETE_EVIDENCE` (items unproven or a required kind of evidence missing).
* **Output**: artifacts, `results.json` and the `summary.json` manifest in `.factory/worktrees/<ticket_id>/evidence/`.

### 6. `/mach-review` — Multi-Agent Consensus Voting Panel & Escalation
* **Model tier**: `contracts` for High risk, `build` for Medium and Low risk, each seat in a fresh context, set per seat by `review.py` and applied to the `reviewer` agent
* **Purpose**: Evaluates a verified cell's diff against `REVIEW.md` with a panel of parallel reviewer sub-agents, each in a fresh context with its own checklist:
  1. *Architectural Scrutiny*: layering, contracts, scope against the plan, dead code, dependencies.
  2. *Security & Performance*: input handling, injection, permissions, secrets, failure behavior, concurrency, resource use.
  3. *Product & UX Validator*: every requirement and exact message against the tests and the captured evidence, and that each `kept` effect's scenario really exercises the shipped rule with this slice's data (M13).
* **The chair does not review.** The skill's own session seats the panel, tells reviewers where to look and never what to find, and carries out the outcome.
* **Votes follow from findings.** A reviewer submits findings, never a vote: any `blocker` is a reject, none is an approve. A blocker must name the rule or spec ID it breaks and the file that shows it. A vote cannot be revised.
* **Consensus Thresholds** (set in `.factory/config.json` under `review`):
  * **High Risk** (Auth, Billing, DB Schema, changes to existing contracts): **Unanimous 3/3 + 1 human approval**. Adding a new contract file does not make a ticket High risk.
  * **Factory tuning** (label `factory-tuning`, rule files only): **Unanimous 3/3 on the contracts tier, no human approval**. Its packet carries `evals`: the latest eval comparison for exactly that change (the branch at the reviewed commit), or "not evaluated" (M14); data for the panel, no threshold.
  * **Medium Risk** (Standard features, UI logic): **Majority 2/3**. An outvoted blocker is reported, not hidden. A blocker from the security seat is never outvoted: it rejects the round whatever the count (`review.security_veto`, on unless a project switches it off). Since M7 any seat may mark a blocker `"class": "security"` with an `impact`; one of high or critical impact rejects the round at every tier, no setting switches that off, and a later round may raise it on any file. The supervisor refuses unattended work while tracked settings switch the veto off, take the security seat off Medium or High panels, drop High-risk human approval, or switch the security scan off (`security.scan.enabled: false`); a person can still run that ticket by hand.
  * **Low Risk** (Docs, wording): **1/1**, one general reviewer.
  * A Silver readiness tier also requires a human approval, whatever the risk.
* **Start gate**: only a cell with a passing verification for exactly the code under review. A change that edits or removes an existing ADR is refused, and so is a `factory-tuning` change that touches the ADR folder.
* **Architecture decisions**: the packet lists the ADRs the change is held to (as they were when it was planned), any exception and the ticket's own proposals; the architecture seat checks the diff against them, and a blocker may cite an ADR by its ID only if it is accepted and in force for the ticket.
* **Policy packs (M14)**: the packet's `policies` lists each pack the spec answers with its kept text and the seats that check it (security: `topic:security`/`topic:privacy`; product: `topic:brand`/`ux`/`accessibility`; otherwise every seat), and each concern its owner accepted as the owner's decision. A blocker may cite `POL-<pack>[-NN]` only when the spec lists the pack, never an accepted concern (`policy-citation`). A `factory-tuning` change that touches the packs' folder is refused.
* **Product principles (M13)**: when the spec answers principles, the packet's `principles` lists those that apply (with the spec IDs that uphold them), those that do not, and each exception as the product manager's decision, not the panel's to reopen. The product seat checks the diff against the ones that apply. `review.py submit` accepts a blocker citing `PP-NN` only when the spec lists it, and never one the product manager excepted.
* **Three-Round Limit**: A ticket gets three judging rounds, counting failed verifications. A rejection in round one or two returns to the build station with `findings.md`; a rejection in round three is `ESCALATE`: the cell is `blocked` and the ticket is labelled `blocked-requires-sme`.
* **Human approval** is recorded with `review.py approve-human`, only on a person's explicit instruction after they have seen the findings. The station never merges.
* **A person may send it back** instead of approving (`review.py send-back`, reached as `/mach send-back <ticket> "<why>"`), only on their explicit word and with their reason in their own words. The reason becomes the finding the builder answers (`person-findings.md` in the round's folder). It counts as a judging round like any rejection: in the last round the ticket is escalated. The lifecycle log records that a person answered and how, never the reason.
* **Security scan (M12)**: `review.py start` runs the shared scan (`scan.py`) on the diff under review and writes `security_scan` into the packet: every secret candidate on its added lines (any the builder overrode marked `overridden_by_builder` with the reason), every dependency its manifests add or change (package.json, requirements and constraints files, pyproject.toml, Pipfile, setup.cfg, setup.py, go.mod, Cargo.toml, Gemfile, pom.xml, build.gradle(.kts), composer.json, *.csproj), lock files changed alone, the names of any scanner reports under `.factory/release/scans/` (never parsed here), and the fixed sentence that nothing was checked against a vulnerability database. A change with a secret candidate or an added or changed runtime dependency is flagged: its security seat runs on `models.contracts` whatever the tier, and a panel without a security seat (Low risk) is reviewed by three seats with Medium's threshold; the packet and decision say why. High, tuning, human approval, the round limit, delta review and the veto are unchanged, and an unflagged ticket is seated exactly as before. The answering seat (security, or a lone general seat) answers every item in `scan_answers`: each secret `real` (only with a high or critical security blocker on that file, so the veto rejects the round) or `not_a_secret`, each dependency `acceptable` or `concern` (only with a finding naming it); `submit` refuses its vote until all are answered, refuses answers from any other seat, and refuses a findings file whose text has a secret's shape. A later round answers only items new since the previous one; earlier answers are carried in the packet. The decision, `findings.md`, the pull request body, `explain`, cleanup's run record (`security_scan` counts, optional) and the lifecycle log (`review.scan_recorded`, counts only) record what was flagged and how it was answered. `security.scan.enabled: false` switches it off; the decision says so. The observe station never proposes a change to it. As built: `docs/mach-next/M12_SECURITY_SCAN.md`.
* **A recorded exception to a security blocker (M12)**: `review.py except <ticket> --finding <round>/<seat>/<n> --by <name> --reason "<why>" [--expires YYYY-MM-DD]`, reached as `/mach except <ticket> <round>/<seat>/<n> "<why>"`, only on a person's explicit word in conversation and refused inside a supervised Factory execution; no unattended instruction or workflow names it. It applies only to a blocker that vetoed (listed in the round's `decision.json` under `vetoing`: a high or critical security-class blocker, or a security-seat blocker under `security_veto`), before a revision has started and while the branch is the reviewed commit; never to a `factory-tuning` ticket; an ordinary blocker is outvoted or fixed, never excepted. The round is recounted: a seat whose every blocker is an excepted vetoing blocker counts as approving (its vote file is never rewritten); a seat with any other blocker still rejects. The exception is accepted only when, with the named findings and those already recorded, the recount meets the tier's threshold and no vetoing blocker is left without one; otherwise it is refused, naming the seat and finding that still block, and nothing is written (several `--finding` in one call, all or nothing). The tally records `blockers_by_seat` and `exceptable` so a veto-only rejection is told apart from one by ordinary blockers. It writes `exceptions[]` into that round's `decision.json` (who, when, the finding, the commit reviewed, the reason redacted and bounded, the expiry), plus `approvals_before_exception`, `approvals_after_exception` and `rejects_cleared_by_exception`, and edits no vote or finding. The round takes the outcome the recount gives, `APPROVED`, or `AWAITING_HUMAN` where the tier or a Silver audit needs a person (High always); an exception is not that approval. It uses no judging round, and works at every tier. Renewal also accepts a branch tip that is the reviewed or revalidated commit plus the merge station's change record commit (`change_record.holds`, M13). `review.security_exception_by` (a list of names, empty by default) limits who may grant one; it guards against accident, not forgery. Expired, it stops the ticket for a person (`security-exception-expired`), who may record a new one or abandon it. As built: `docs/mach-next/M12_SECURITY_EXCEPTION.md`.
* **Review noise (M15)**: a note may carry `weight` `important` or `nit` (none reads as important, so earlier notes keep their meaning; a security finding is never a nit). `submit` keeps a seat's first `review.nit_cap` nits (default 5) and records the rest as `nits_dropped` in the vote; blockers and important notes are never dropped, and no vote, threshold, veto or round rule reads a note. `findings.md`, the pull request review and the change record show important notes, the kept nits and the count. `review.py rate <ticket> --finding R/SEAT/N --useful|--not-useful [--by]`, on a person's word and never unattended, writes the round's `ratings.json` (never a vote file); cleanup's run record carries the ratings (`finding_ratings`) and each note's weight for the observe station. `templates/REVIEW.md` says what Important means and what not to report. As built: `docs/mach-next/M15_VERIFY_REVIEW.md`.
* **Output**: `review/round-N/` in the cell with the packet, diff, each vote, `findings.md` and `decision.json`; cell stage `approved`, `awaiting-human`, `built` (rejected) or `blocked`.

### 7. `/mach-cleanup` — Workspace Teardown & Hygiene Engine
* **Model tier**: `utility` (low effort) when run as its own agent; the skill does not pin a model. `cleanup.py` does the work.
* **Purpose**: After a ticket's branch is merged, or the ticket is abandoned, keep the artifacts, remove the rest, and leave a record of how the run went. This is the only station that deletes anything.
* **Order**: plan (a dry run that changes nothing) → archive → check the archive → remove the worktree and cell folder → delete the local branch → append the run record. If archiving fails, nothing is deleted.
* **Archive**: `.factory/archive/<ticket_id>.tar.gz` with everything in the cell folder except the `repo/` checkout; an earlier archive is never overwritten.
* **Gates**: the branch must be merged into the default branch and the cell `approved`. A squash or rebase merge is accepted with `--merged-as <commit>`. Uncommitted work blocks a normal run. The script deletes only `.factory/worktrees/<ticket_id>` and refuses symlinked cells, a branch that is not `feature/<ticket_id>`, and unusable ticket IDs.
* **Abandoning** (`--abandon "<why>"`, only on a person's explicit request): uncommitted work and a git bundle of the unmerged branch are saved into the archive first, so the work is recoverable.
* **Run record**: one line per finished ticket in `.factory/archive/runs.jsonl` (outcome, judging rounds, verification failures, review blockers with the rules they broke, builder deviations), which the observe station reads. Since `record_version` 2 it also says what landed (`integration`: branch, target, method, approved, landed and merge commits, pull request) and, for product work, which slice revision it built (`product`: slice ID, revision, epic ID, digest, source, source commit, and the slice's issue when it came as one), and (optional, M13) the merge station's change record (`change_record`: path, SHA-256, commit), and the slice's Jira key (`jira`, M13 E).
* **Publishing the archive (M13)**: `records.publish_command` in `.factory/config.json`, a list of strings in the style of `tickets.commands`, run once without a shell after the archive is written and checked (`{archive}` its path, `{ticket}` the ticket ID; with no `{archive}` the path is the last argument). Its result is recorded in the run record (`records_publish`); a failure never blocks cleanup. For a team that must keep the evidence files the change record names by hash.
* **Re-plans**: the branch tips a re-plan saved under `refs/mach/replan/<ticket_id>/` are bundled into the archive, checked, and only then removed.
* **Never**: merges, pushes, deletes remote branches, or changes code on the main checkout. Code formatting belongs to the build station's lint gate, not here.
* **Also**: `orphans` lists finished or broken cells; `status` lists every cell. The ticket is closed with the ticket skill after a successful run.

### 8. `/mach-observe` — Meta-Learning & Self-Improvement Loop
* **Model tier**: `planning` (high reasoning) when run as its own agent; the skill does not pin a model
* **Purpose**: A closed loop that tunes the factory's own rules from its finished tickets. `observe.py` measures and files; the model interprets and proposes; the line applies; the review panel decides.
* **Input**: `.factory/archive/runs.jsonl`, the record cleanup writes for every finished ticket: rounds, review blockers and the rules they broke, reviewers' non-blocking notes, builder deviations, verification failures. Plus open cells and the last audit.
* **Scorecard** (targets in brackets): average judging rounds per merged ticket (< 1.3), first-pass rate (> 85%), escalation rate (< 5%), share of tests seen failing first (> 90%), abandonment rate, deviations per ticket.
* **Patterns**: review blockers grouped by the rule they broke, deviations by type, verification failures by kind (each needs 2 tickets and 15% of the sample), and themes recurring across at least two tickets' reviewer notes.
* **Proposals**: the smallest rule that would have prevented each pattern, targeted at `REVIEW.md`, `CLAUDE.md`, `AGENTS.md` or a skill's instructions, citing the tickets that prove it. `observe.py report` refuses proposals without evidence from the sample, aimed at any other file, numbering more than five, or made on fewer than five finished tickets.
* **Closing the loop**: `observe.py file-ticket` files one ticket labelled `factory-tuning` carrying every proposal. It goes through grooming, build, verification and review like any other ticket, so each rule change is a reviewed, revertible diff. Rules are never edited directly.
* **Trigger**: after every `observe.every` finished tickets (5 by default), cleanup and `/mach status` report that a pass is due; `/mach` and the belt workflow start it with `--auto` and the workflow then runs the tuning ticket.
* **Control bands (M15)**: `observe.py bands` (`/mach bands`) watches each scorecard measure as one value per finished ticket: a baseline of up to `observe.bands.window` (30) tickets before the most recent `recent` (8), mean and sample standard deviation, and the four Western Electric zone rules (NIST/SEMATECH e-Handbook 6.3.2) checked at each recent ticket; below `min_sample` (20) the answer is "not enough finished tickets yet". Tiers in `observe.bands` (tracked): 1 records (`bands-log.jsonl`), 2 adds one fixed line to `/mach status` (`control_bands`) and the observe report, 3 also makes an observe pass due (run.py's `observe_status`, once per breach); a shift for the better is only recorded. `bands dismiss <measure> --reason` is a person's word; the breach returns only after the measure goes back inside and leaves again. Deterministic, read-only apart from its two records; never starts an agent, files a ticket, or changes a rule or threshold.
* **Never an ADR**: observe never proposes a rule that targets an architecture decision record, and a tuning ticket never accepts, changes or supersedes one; the review station refuses a tuning change that touches the ADR folder.
* **No person for tuning**: a `factory-tuning` ticket is decided by a unanimous three-seat panel on the contracts tier, with no human approval, provided its diff touches only rule files and its own spec and tests (the merge station's change record, the path in `cell.json` `change_record`, is not judged). Reviewers must block any change that removes a rule, weakens a gate, lowers a threshold or raises a limit. Observe never proposes such a change: those stay a person's decision.
* **Output**: `.factory/observations/metrics.json`, `observation-<date>.md`, `last-pass.json`, and the tuning ticket.
* **Factory evals (M14)**: `skills/observe/scripts/evals.py`, reached only as `/mach eval` (section 5). Observe never starts it.

### `/mach-idea` — Intent from Anyone (M14 part D)
* **Purpose**: one person who is not an engineer describes an idea in their own words, one plain open question at a time, until five parts are concrete: problem, proposed outcome, affected users and systems, constraints (with what is out of scope), open questions. It never invents a fact (unknowns become open questions) and never promises the idea will be built. The person sees and corrects the result before anything is sent.
* **The template**, defined once in `issue_rules.py` (`idea_body`, `parse_idea_body`, `idea_questions`, `idea_fence`): a hidden marker `<!-- mach:idea v1 -->` and the five headed parts; the parser returns the parts cleaned, redacted and bounded, or None for anything not exactly the template. The SKILL.md carries the same text for where no script runs; a test holds the two together.
* **Three ways out**: in Claude Code with `gh` and a GitHub `origin`, `scripts/idea.py check` prints the exact text (redacted; anything shaped like a credential, by `scan.py`'s shapes, is refused) and `file --sha256 <from check>` creates the issue only for that text, on the person's yes; with a GitHub connector on claude.ai or Cowork the skill files the same text through it; otherwise it gives the text to paste. The issue never carries a label: someone with write access adds `mach:request`, so the M8 acceptance rule is unchanged. Kept out of unattended runs (`executor.NOT_FOR_THE_FACTORY`).
* **In Product Studio**: `request list` marks a templated request (`idea_template`), `request show` gives its five parts apart (`idea.parts`, each fenced), and `request pick` and `slice resume` carry its open questions as `request.questions_to_ask_first`, read fresh from the text kept at pickup, never stored in the work order (whose `origin` holds identifiers only). The interview asks them first; the request's text never answers them. As built: `docs/mach-next/M14_IDEA_INTAKE.md`.

## 5. End-to-End Factory Conveyor Belt

```text
┌────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│                                       THE MACH CONVEYOR BELT                                           │
└────────────────────────────────────────────────────────────────────────────────────────────────────────┘
  1. INGEST & AUDIT ──► 2. GROOM & CONTRACT ──► 3. CELLULAR TDD ──► 4. DYNAMIC QA ──► 5. CONSENSUS REVIEW
    /mach-ticket          /mach-intent             /mach-build         /mach-verify         /mach-review
    /mach-audit            (planning, contracts)    (build)             (build)             (contracts, build)
                                                                                                  │
  8. META-OBSERVE   ◄── 7. TEARDOWN       ◄── 6. MERGE          ◄─────────────────────────────────┘
    /mach-observe         /mach-cleanup           /mach-merge
    (planning)            (utility)
```

### Orchestration: `/mach` and the belt workflow

The order of the belt is decided by a script, not by whoever is driving. `skills/run/scripts/run.py next <ticket>` reads what every station recorded (the cell's stage, the audit report, the verification and review decisions) and names the single next step, the worker for it, and its model tier; or it stops and says what the ticket is waiting for.

| Cell stage | Next step |
|------------|-----------|
| no cell, `interview`, `spec-open` | groom (intent); in headless mode a spec with open questions stops for a person; a spec held only by an open policy concern stops in either mode (`policy-owner`); a slice taken in from Product Studio but not dispatched, with no cell or a cell at `interview` whose dispatch was cut short, stops (`dispatch`) and is never groomed |
| `spec-ready` | plan (intent stage 2); stop if the contract engineer asked the product manager a question (`product-answer`), the plan cannot follow an accepted ADR (`adr-decision`), an ADR on main cannot be read (`adr-fix`), or a required topic has no accepted ADR on main (`adr-baseline`) |
| `planned` | stop if High risk and its own proposed ADR is not accepted (`adr-acceptance`); audit if the report is missing or stale; stop if Bronze and not a hardening ticket; otherwise build |
| `building` | build (resume) |
| `built` | revise if verification failed or review rejected this build; otherwise verify |
| `verified` | review |
| `awaiting-human` | stop: a person approves |
| `approved` | merge, if the settings let the line merge this risk tier; otherwise stop for a person to merge |
| `pr-open` | merge again: check whether the pull request can land |
| `merged` | cleanup, and an observe pass when one is due |
| `blocked` | stop: escalated to a person |

Two drivers use it:

* **`/mach <ticket>`** (a skill): a line supervisor in one conversation moves one ticket station to station, starting a fresh sub-agent for build, verification and each review seat, and stopping wherever a person is needed. `/mach status` shows every ticket's next step.
* **The `mach:belt` workflow (a Claude Dynamic Workflow, `workflows/belt.js`; named `mach-belt` in a project install)**: runs several tickets unattended and in parallel, each in its own cell. The workflow script holds no knowledge of the order: it locates `run.py` once, then asks it what is next through a relay agent given the exact command, starts the worker it names, and asks again, with a cap on steps and a stop when a station runs twice without moving the ticket.

Neither driver grooms interactively on a person's behalf or approves a high-risk change. Whether the line merges is a project setting.

**Several tickets (M9).** `/mach <a> <b> <c>` shows a schedule and then starts the belt for those tickets. `skills/run/scripts/schedule.py` (`run.py schedule`) decides what may run together; it reads only. Rules, in the order the tickets were given: never more than the ceiling in force (`factory.max_parallel`); a ticket waits for the tickets it depends on to be integrated; at most `factory.max_parallel_high` (default 1) High-risk tickets at once; two tickets whose plans' file touch maps overlap never run together. A ticket with no plan yet runs only as far as the build station, then is scheduled again. `--limit <n>` and `--sequential` lower the ceiling; Claude may run fewer and says why; only a person raises a ceiling, in settings or for one run (`--by-person`, at most 8, refused inside a supervised execution). The belt asks the script each time a place frees and keeps only what it names; the supervisor applies the High-risk and overlap rules before it starts an execution, and inside an execution the schedule counts the supervisor's other live executions, so a ticket planned there is checked again before it builds. `/mach` with no ticket stays the status view and starts nothing. Design: `docs/mach-next/M9_DESIGN.md`.

**Pull what is ready.** `/mach pull [--limit n] [--sequential] [--dry-run]` is the engineer's one command for running the Factory on whatever product work is ready (`run.py pull`, `skills/run/scripts/pull.py`). Under the intake lock it takes in every slice marked ready (intake's reconcile, with its acceptance checks; what is not accepted is listed with its reason and never built), chooses the next batch with the schedule's own rule (`schedule.decide`) over the tickets already in the line that can move and then the slices the plan marks dispatchable, in the plan's order, and dispatches the chosen slices through intake's guarded dispatch, the engineer's `pull` being the explicit command it requires. It adds no rule: the plan says what is ready, the schedule what may run together, `run.py next` each ticket's next station. Tickets in the line count against the ceiling and are carried on in the same run; a ticket whose next step is a stop, whatever it waits for, is listed for a person with the script's own sentence; a claimed ticket is left to its worker; a cell whose dispatch was cut short is not in the line, and its slice is dispatched again in the plan's order; a ready slice beyond the ceiling waits for a later pull. It prints the schedule in plain words (`--json` for the skill) and the exact tickets to run; the skill then starts the belt for several or drives one in the conversation, and ends with the walkthrough of decisions. `--dry-run` changes nothing. Refused inside a supervised execution; it reads no machine-local authorization and enables nothing, and the supervisor (`/mach factory`) remains the unattended way.

**One worker per ticket (M9).** A driver that is handed a work step claims it: `run.py next --holder <token>` writes `.factory/worktrees/<ticket_id>/claim.json` through one shared helper, `skills/intent/scripts/claim.py`, and the intent skill claims `plan` with `cell.py claim` before it starts the contract engineer. While another holder's claim is fresh (the cell is still at the stage it was made at, and it was made or renewed less than `factory.claim_minutes` ago, 90 by default), `next` answers `stop` with `needs: "worker-in-cell"`, the schedule holds the ticket, and `status` shows who is at work since when. A stop is never claimed, and a call with no holder writes nothing. Only a person's explicit word takes a claim over (`--take-over`). It guards against two honest drivers colliding; it is not a security boundary, and it changes no station's result.

**The walkthrough of decisions (M9).** When work stops for a person, the run skill walks them through each waiting ticket: what happened, then a prompt with that ticket's options. `skills/run/scripts/decide.py` (`run.py decide [<ticket>...]`) lists the options and reads only; it lists only what a station's script really accepts in that state, and marks one as recommended only where a rule decides it. Approving or rejecting a change is never recommended by rule. The skill routes the choice to the station that owns it, under its own gates, and asks for any reason in the person's own words. It starts on its own at the end of `/mach <ticket>` and of several tickets, and never unattended: not in the belt, not headless, and the script refuses it inside a supervised execution. One route was added for it: `/mach replan <ticket> "<why>"` (the intent station's `cell.py replan`). The ADR stops add two more: `/mach adr except <ticket> <ADR-NNNN> "<why>"` (`cell.py adr-exception`) and `/mach adr accept <ticket> <ADR-NNNN>` (`cell.py adr-accept`). M12 adds `/mach except <ticket> <round>/<seat>/<n> "<why>"` (`review.py except`), offered, never recommended, only where the script would accept it (the recount with every vetoing blocker excepted passes): for an escalated round, for a ticket a person names after such a rejection (before the builder revises), and to renew an expired exception.

Three aids sit beside the state machine and change nothing it decides:

* **Digest**: `next`, `status` and `explain` open with three lines: where the ticket stands, what a person must decide, and time and cost. A cost appears only where one was recorded (supervised executions in the intake ledger); otherwise it reads "not recorded". It is never estimated. Since M15 they also carry `rules_changed`, one fixed line each when the product principles, a policy pack or a shipped rule the spec names changed after the spec answered it (`cell.py rules_changed`): principles from the folder are read at the main checkout's HEAD, principles from GitHub are compared with the newest copy any cell here fetched (GitHub is never asked). Flag only, like ADR timing. `decide` walks the `policy-owner` stop (the owner's acceptance or the interview, neither recommended) and `explain` names the open concern's pack, statement and owner from the cell's spec.
* **`/mach explain <ticket>`** (`explain.py`): why a ticket failed, was sent back or is waiting, from the stations' own files: the requirement or scenario, the failing check, each reviewer blocker with the rule it cites, rounds used. It reads only, never opens an archive, and passes reviewer and verifier text on as bounded data.
* **`/mach current <epic>`** (`current.py`, M13 part C): how an epic works today, compiled from the slice specs on the integration branch at one commit (`--at` names another): every invariant, requirement and decision rule in force, each naming its slice, read through the one parser of `## Effects on shipped behaviour` (`skills/intent/scripts/effects.py`): a rule a later slice replaced or retired is gone, a changed or replaced one is shown as the later slice's rule with what it took the place of, a kept one with the scenario that confirmed it, also across epics. Rules of slices with no such section are "not yet reconciled"; a section with problems is listed and never applied. Later means slice ID order. Reads Git objects only, with or without `.factory/`; `--json` adds every shipped rule (`rules`). As built: `docs/mach-next/M13_CURRENT_VIEW.md`.
* **`/mach doctor`** (`doctor.py`): checks Git and worktrees, Python, Claude Code, tracker sign-in, the MACH install and the project's rule files, and (M20 A2, a github.com origin only) `merge.protection`: whether the integration branch requires branches to be up to date and status checks to pass before a merge, read with two read-only `gh api` calls (the branch's active rules, then its classic protection), `warn` with the fix when not, `not_checked` when it cannot be read; and `merge.method`: with `merge.method` `local` or unset and a github.com origin, a `warn` with the fix (`"pr"` for a team) when more than one collaborator can push (one read-only `gh api .../collaborators` call; whether others push cannot be seen from Git), `not_checked` when that cannot be read; works before `.factory/` exists. Its `workspace` check makes and removes a throwaway ticket workspace under `.factory/worktrees/` the way `cell.py open` does (detached, so no branch), and fails with the fix when Git is older than 2.36 or cannot make it; this is the one thing it writes without `--fix`. `--fix` only creates missing MACH folders. It never reads `.factory/local/`, never shows a tracker's sign-in output, and enables nothing.

The things a person asks for by name also go through the run skill, which routes each to the station that owns it under that station's own gates: `/mach send-back <ticket> "<why>"` (review's send-back), `/mach except <ticket> <round>/<seat>/<n> "<why>"` (review's security exception: the skill shows the finding first and never offers it unprompted), `/mach approve <ticket>` (review's human approval; the skill then carries the ticket on to the next step the script names, so no second command is needed, and the project's merge settings still apply), `merge <ticket>` (the merge station, by a person), `abandon <ticket> "<why>"` (cleanup), `new "<idea>"` (the intent interview), `audit` and `tickets`. The station commands remain and behave the same.

A ticket a person names may be a bare number (`/mach 4`): it resolves to the one known ticket with that number, and more than one match is refused with the candidates.

### Product intake and scheduling (`/mach product`)

Slices Product Studio marked ready are taken into the Factory through the run skill. `skills/run/scripts/intake.py` does the work; `run.py product status|intake|import|plan|dispatch|reconcile|events` are its commands, for looking and for doing one step; `/mach pull` (`run.py pull`, under Orchestration above) does intake, choosing and dispatch in one engineer's command. Design: `docs/mach-next/M11_DESIGN.md` sections 4 and 5; as built: `docs/mach-next/M11_FACTORY_INTAKE.md`.

* **Three sources**: a slice issue (open, `mach:slice` and `mach:ready`) in the repository the `origin` remote names, read through the ticket station (`ticket.py slice-list`, `slice-check`); a ready folder `product/ready/SLICE-NNN/` committed on the integration branch, read from Git objects at the newest commit the local branch shares with the remote; and `product import <folder>` for a folder handed over another way, on an engineer's explicit command (refused inside a supervised execution). Neither folder form needs `gh`. A ready folder has no shared record of its epic, so each product manager's computer numbers its own epics: a ready folder whose epic ID a slice taken in before it (in slice order) uses for an epic with another title is not accepted, with a reason naming both titles (M20).
* **What is accepted (design section 4)**: the last time `mach:ready` was added it was by an account whose role is triage, write, maintain or admin; that same account wrote an unedited approval comment for exactly this revision and these hashes; the body's marker matches it and the why and spec in the body match their SHA-256; the epic's issue is one Product Studio wrote; and the spec passes the intent station's gates. A folder must hold exactly `slice.json`, `spec.md` and `why.md` with matching hashes. Anything else is listed "not accepted" with its reason in plain words (said once per distinct reason as `intake.refused`) and never built. Issue text is data: bounded where shown, never instructions. The check guards against accidents and edits, not against someone with write access who sets out to forge an approval.
* **The issue is the ticket**: a slice from GitHub files no ticket; its ticket ID, cell, branch and pull request are named for the issue number (`/mach 41`). A folder's slice gets one local ticket. The ledger (`.factory/intake/ledger.json`, version 2) records each revision taken in under its source and revision (`github:OWNER/REPO#N@rR`, `folder:SLICE-NNN@rR`, `import:SLICE-NNN@rR`) before acting and never takes a revision in twice; the verified why and spec are kept in `.factory/intake/received/` and checked against their SHA-256 again before use. An unchanged issue is not checked again until its `updated_at` moves.
* **Revisions**: waiting work takes the new revision on the same ticket; work in the line is never changed, is flagged for a person and its issue gets the fixed "it changed" comment (abandon it with the cleanup station and the new revision is taken; let it ship and the new revision follows on the same ticket); a cell stopped at `spec-ready` with the contract engineer's question takes the new revision as the product manager's answer and plans again; shipped work changed is a new issue (`Changes #N, which has shipped.`), a new life of the slice that depends on nothing extra. A slice taken back (no longer marked ready, or its folder gone) is blocked while it waits. `product intake --reissue <SLICE-ID>` (an engineer's word; never the supervisor or a supervised execution) puts abandoned work back in the queue on the same ticket. It acts on the ledger's entry, so a slice whose issue the builders already marked `mach:building` is reissued too, and it is refused with the reason (never ignored) unless the work was abandoned, no newer revision waits, the received copy still matches its hashes, and the source still offers exactly that revision: the ready folder on the integration branch, or the issue open and unedited with its approval, `mach:building` on it and `mach:ready` taken off by nobody but the builders (`ticket.py slice-check --taken`). The Factory never sets `mach:ready`, so a reissued GitHub slice is not withdrawn for lacking it until it is dispatched again; it is withdrawn if its issue is closed, edited or taken back meanwhile.
* **Scheduler**: every slice is `completed`, `active`, `ready` or `blocked`, with reasons. A slice waits until every slice it depends on is merged, checked in Git (or, for one this Factory never took in, its spec with that issue in its header is on the integration branch; for one it took in, M20, its approved spec for that very revision, by SHA-256 without the header, is on the integration branch; when this Factory never put it in the line or put its copy aside, the slice is `completed` with "Another Factory built it", and nothing is written to its issue from here); then the product manager's order within the epic (sub-issue order, the task list, or slice ID for folders); then oldest ready first. `factory.max_parallel`, `max_parallel_high`, file overlap and claims are unchanged.
* **Dispatch**: only on an engineer's explicit command, or the supervisor's with an authorization. A slice is named by its ID or its issue number. It opens the cell, writes the spec into `specs/slices/` with one header line under its title (`> Epic: <name> (EPIC-NNN, issue #N). Slice issue: #N.`), writes `intent.md` from the why, passes `cell.py finalize --from-studio SLICE-NNN` (which commits the spec on the ticket's branch; the product manager's draft of the same slice on this computer is not a duplicate of it) and stops at `spec-ready`. It starts no agent. Product-sourced work is never reviewed below Medium. `run.py next` on a ticket taken in but not dispatched stops with `needs: dispatch`, and never grooms it. A dispatch cut short (the cell opened and the spec written, `finalize` refused, so the ledger has no `dispatched_at` and the cell is at `interview`) is not in the line: `run.py next` stops it with `needs: dispatch`, the plan marks the slice `interrupted` and offers it again, and the next `/mach pull` or `product dispatch` finishes the same cell with the spec already written there. A refusal for `duplicate-slice-id` says that one of the two slices needs a new number.
* **Factories keep out of each other's way (M20)**: several engineers' Factories, attended or supervised, take slices from one repository. No slice belongs to anyone in advance; two Factories do not build one slice at once. *The claim*: immediately before a cell is opened for a slice from an issue, by any caller (an engineer's dispatch, `/mach pull`, the supervisor), `ticket.py slice-claim` reads the issue again (open, `mach:slice`, still this slice and revision), reads its comments, posts a claim unless one already holds it, reads the comments again, and the Factory goes on only if its claim is the one that holds. A claim is a comment in a fixed template (`issue_rules.claim_comment`) ending `<!-- mach:claim v1 slice=SLICE-NNN revision=R factory=<token> -->`; the token is 16 hex characters of SHA-256 over a random value the Factory keeps in `.factory/local/factory.json` (never committed or posted) and the slice ID, so a Factory is never identified by its GitHub account alone. A claim counts while it is exactly the template, unedited, by a person with the triage role or above. `issue_rules.claim_holder` decides: only claims at or after the latest take-over count; of those, the earliest live one for this revision (GitHub's comment order, never a clock), else, while the issue carries `mach:building`, the earliest live one on another revision; `mach:building` with no claim holds too. A claim is live while its last activity (the claim, a later MACH status comment by the same account, or the last commit on `origin/feature/<issue>` as last fetched) is within `intake.claim_stale_days` (default 3). The claim comment is the claim, not the label: a `mach:building` write still in the outbox leaves the slice held. A Factory's own earlier claim counts as its own. *Skipping*: `slice-list` lists open slice issues with `mach:ready` and those with `mach:building` (`slice-check --taken`); intake takes them in and records `held_by`; the plan blocks a slice held elsewhere with "SLICE-NNN is being built by @login since <time> UTC" (`being_built_elsewhere`), so pull and the supervisor take the next slice nobody is building; a stale holder is shown as "Claimed by @login, no activity for N days: free to take" and does not block. A Factory that loses a race at dispatch opens no cell and no branch, edits its own claim into the withdrawn form, records `claim_lost` and `held_by`, emits `intake.refused`, and reports "SLICE-NNN is being built by @login since <time> UTC. Nothing was started here."; `/mach pull` then dispatches the next dispatchable slice in its place. Pull says "Everything ready is being built by other Factories, so nothing new starts here." when that is so. A slice reopened and marked ready again stays with its builder: other Factories see it as held. *Releasing*: abandoned work withdraws its claim ("Its work there was stopped."; a reissue on the same machine claims again); a stale claim holds nothing; and `product dispatch <slice> --take-over`, an engineer's explicit word only (refused with `--ready`, for any caller but an engineer, and inside a supervised execution), posts a take-over claim ("The MACH Factory is taking over SLICE-NNN revision R, on a person's word: the earlier claim on it no longer holds.") after which only later claims count. When GitHub cannot be reached, nothing is started and nothing is made. When a claim is won, an open pull request from `feature/<issue>` is reported in the dispatch result. *The backstop*: the shared main takes a slice revision once. `intake.already_landed(root, slice_id, spec_sha256, refs)` finds this revision's approved spec on the local main or `origin/<main>` and the commit that first brought it there; `run.py next` asks it for a cell intake opened (before merge, unless the cell's own branch is merged or a pull request is open) and stops with `needs: landed-elsewhere` and "SLICE-NNN was already shipped from another Factory (merged as <commit>). This copy was not merged.", naming `cleanup run <ticket> --abandon "<why>"` (the branch's commits are kept in the archive's `branch.bundle`). The merge station (`merge.py run`) makes the same check itself, with the same function loaded from the run skill by path: after its fetch of `origin/<main>` and before it merges locally, pushes, opens a pull request or merges one, and again after each re-fetch when the shared main moved. For a cell with `product` (an engineer's own ticket has none), when this revision's spec is on the local main or `origin/<main>` and what landed is not the cell's own (no `merged` record, its branch's commit is not on that branch, and with method `pr` its own pull request is not merged), it refuses (`landed-elsewhere`) with the same sentence and "Nothing was pushed or merged.", merges, pushes, opens and closes nothing, and leaves the cell for cleanup; a pull request of its own already open stays open, with a note to close it on GitHub. In the same place it refuses (`slice-id-taken`) a spec the branch adds whose slice ID is already on the main branch under another file name, unless it is the same slice (`cell.py handed_over`, the 0.20.0 rule): two engineers took one number, and Git sees no conflict. A slice not yet dispatched whose revision is on `origin/<main>` but not the local main is blocked with "Update your main branch". `mach:shipped` and closing the issue come only from the Factory whose own merge is on its integration branch. A newer revision has another SHA-256 and is new work. Slices from ready folders are not claimed.
* **Design mocks (M14 C)**: a slice issue with design mocks is held, listed under `not_accepted` with `waiting: mocks` and a plain reason, never taken in, until every picture its approval names is committed at `product/ready/SLICE-NNN/mocks/<sha256>.<ext>` on the integration branch and matches its hash and content; a folder must hold exactly the pictures its `slice.json` lists. The mocks' digest is part of the revision's digest; the pictures are kept in `received/` and dispatch writes them to the cell's `mocks/` with `manifest.json` (`cell.json` `product.mocks`). A slice without mocks is unchanged. Pictures are never fetched from an address or taken from issue text.
* **The builders' question**: when the contract engineer finds a spec defect only the product manager can settle, it records it with `cell.py spec-question <ticket> --question "..."`; the ticket stops with `needs: product-answer` until a new revision arrives.
* **A small change (M18)**: a slice's `small` record (from the marker, checked against the approval, which must carry the same: else "Not accepted: whether it is a small change is not what was approved"; or from `slice.json`, checked by `issue_rules.is_small_record`) goes into the ledger entry (`small`, only for one) and is part of the revision's digest, so a revision that only left the light path is a new revision. Dispatch, and a new revision given to a cell, write `kind`, `small` and `widened` (the rule's sentence, or a fixed line on the PM's word) into `cell.json` before `cell.py finalize`, which exports them to `spec.json`. A cell stopped because a rule says it is not small asks the PM through the builders' question; their revision that comes back widened settles it. A slice that is not small is taken in exactly as before.
* **Status back to the issue** (`ticket.py slice-status`, fixed templates with a hidden marker, recorded in the ledger before tried, retried on the next pass, never blocking): `mach:building` when the cell opens (taking off `mach:ready` and `mach:question`); `mach:question` with the question, redacted, bounded and unable to mention or link anyone; `mach:shipped` and closing the issue once the merge is seen on the integration branch; a comment when the cell is blocked; and the "it changed" comment. When a slice ships (M13), one comment on its epic's issue holding the epic's current view at the integration branch's head (`ticket.py epic-view`, `issue_rules.epic_view_comment`: a marker with the epic and commit, a heading, one fixed sentence, then `current.py`'s `epic_markdown`, under GitHub's limit with a note when cut), found by its marker and the Factory's own account and edited in place, created only when there is none; every other epic whose rules the slice changed, replaced or retired gets its comment replaced too. Only an epic issue Product Studio wrote; nothing for a slice from a folder. `tickets.github.status_comments: false` stops comments, never labels or closing. The Factory writes nothing to a request's issue: the slice issue carries no request.
* **Events**: each ledger transition is appended to `.factory/intake/events.jsonl` (schema version 3: `epic_id` and `issue` in place of `wave_id` and `project_id`), for the supervisor and the Factory Floor.
* **Ready for a supervisor**: `product reconcile` is intake plus a recorded plan plus the status writes in one step; intake, reconcile, import and dispatch hold a lock so there is one writer at a time; and any caller but an engineer must bring an authorization to dispatch, or nothing is dispatched.
* **Never**: runs in the background, reads the machine-local Factory policy, fetches unless asked, changes the main checkout, merges or pushes.

### The Factory Supervisor (`/mach factory`)

On a machine whose engineer has enabled it, a supervisor keeps approved product work moving unattended. It is off on every machine until enabled there. Code: `policy.py`, `executor.py`, `supervisor.py`, `service.py` and `activation.py` in `skills/run/scripts/`. Design: `docs/mach-next/M4_DESIGN.md`.

* **Authorization is machine-local**: `.factory/local/runner.json`, git-ignored and private. Missing, malformed, written on another machine or for another folder all read as disabled. The project's tracked settings (`factory` in `.factory/config.json`) can restrict it and never widen it; product files are never read for it.
* **Activation**: `factory enable` runs a preflight and prints exactly what would be allowed and a short-lived code; only `factory enable --confirm <code>`, on a person's explicit yes, enables. Two modes: **observe** (discover, take in and plan; start no agent) and **supervised** (also run eligible work, stopping at every human gate). `status` changes nothing. `pause`, `resume`, `disable` and an emergency `stop` complete the lifecycle.
* **It decides nothing about order**: each pass calls intake's `reconcile` (the slice issues marked ready and the ready folders, verified and scheduled, and the status writes), dispatches through intake's guarded `dispatch` with an authorization read from disk at that moment, and starts the existing belt workflow for one ticket per execution. `run.py next` and every station gate stay authoritative.
* **Execution**: one `claude -p` per ticket, in an explicit restricted permission mode, with an explicit tool list, a spending limit and a known session ID, behind a detached wrapper that records its start and end. A tool outside the list is refused and raised to a person, never granted. By default every execution stops before the merge station.
* **Recovery**: a claim is on disk before a process exists. A restarted supervisor tells apart a claim that never started, an execution still running, one that ended unwatched and one whose outcome is unknown. Unknown outcomes are counted or raised to a person; a lost merge or cleanup is never retried automatically.
* **One runner per project, per machine**: an ownership lease with a heartbeat. Across machines, several engineers' supervisors on one repository dispatch through the same claim on GitHub as an engineer's dispatch (M20, above): each skips a slice another Factory is building and builds only what it claimed, and a supervisor never takes a slice over. Slices from ready folders are not claimed.
* **Monitoring requests (M8)**: off unless the engineer enabled the Factory with `--monitoring-requests` (supervised only; `runner.json` `monitoring_requests`, missing reads false; tracked `factory.monitoring_requests: false` forbids it and `true` grants nothing). `monitoring.py` then takes in GitHub issues that a listed monitoring account (`tickets.github.monitor_accounts`, matched on numeric id) filed and labelled itself: one per fault, at most three groomed per pass, oldest first, after product work is scheduled. Each runs in two executions: headless grooming and planning, then the build only when the cell's risk tier is below High and within the machine's limit; never reviewed below Medium. An issue a person labelled goes to Product Studio only. `/mach requests monitor` is the engineer's explicit form and starts no agent. This is the one place the supervisor runs work that did not come through intake's dispatch. Design: `docs/mach-next/M8_DESIGN.md` (D7).
* **No operating-system sandbox** around an unattended execution: it may run `python3` with the engineer's home folder and network. `factory enable` states this and the engineer accepts it explicitly.
* **Optional, each on explicit request**: advisory Git hooks (a wake-up note, never authorization), fetching on a timer, and a per-user macOS LaunchAgent. None is installed by cloning, installing or running a ticket.

### Notifications (`/mach notify`)

A person is told when a ticket that nobody is watching stops for them: by one outbound message to a channel, by a macOS Notification Center banner, or both. Off on every machine until a person turns a channel on there. Code: `skills/run/scripts/notify.py`. Design: `docs/mach-next/M10_NOTIFICATIONS.md`.

* **The address is machine-local and secret**: `.factory/local/notify.json`, private and git-ignored, bound to this machine and folder. Missing, malformed or written elsewhere reads as off. No tracked file can turn notifications on or supply an address; `factory.notifications: false` in the tracked settings forbids them, including the test message. The address is read from a file or an environment variable the person prepared (`notify set --from-file|--from-env`), never from the conversation or a command line, and is never printed or logged; status shows the host only.
* **When**: `run.py next <ticket> --headless` answers a stop a person must act on (a run of several tickets, or any unattended run by hand); a supervised execution ends with its ticket waiting; the supervisor parks a ticket; or an approved ticket waits because this machine does not merge unattended. A person driving one ticket in conversation gets none. Inside a supervised execution `run.py` neither sends nor reads the address: the supervisor sends.
* **Once per wait**: keyed by ticket and stage in `.factory/local/notify-state.json`, recorded before sending.
* **What it says**: fixed words and identifiers only: the label the person chose, the ticket ID, the script's fixed sentence for that wait, and the command (`/mach decide`). Never a title, reviewer or verifier text, a path, a commit, a name or a link.
* **Sending**: standard library, one POST, five seconds, redirects refused. A failure changes no result, step or exit code; it is retried while the ticket still waits, five attempts in all, then given up and shown in `notify status`.
* **The banner** (`notify banner on|off`, macOS only; refused elsewhere, and a stored switch on another system reads as off): `/usr/bin/osascript` with no shell and a fixed script, the words passed as arguments and never written into the script. Same triggers, same fixed words, once per wait on each channel that is on; the channels fail and retry independently. "Ran" means the command exited 0: MACH cannot see whether macOS showed it.
* **Never**: listens, approves, starts or changes anything; nothing but `run.py` and the supervisor it builds reads the address, and `doctor`, `explain`, `decide`, intake, release qualification, Product Studio and the observer never do.

### Self-reporting (`/mach report`)

MACH records its own defects on the machine where they happen and files one as a GitHub issue on MACH's repository only on a person's yes after they read it. Code: `skills/intent/scripts/faults.py` (recording, shared by every script), `skills/run/scripts/selfreport.py` (`run.py report`). Design: `docs/mach-next/M14_DESIGN.md` part E; as built: `docs/mach-next/M14_SELF_REPORT.md`.

* **Recording**: every script with an entry point (each `skills/*/scripts/*.py` with a `__main__` block, and `bin/mach`) carries two lines before `sys.exit(main())` that load `faults.py` by path and install a hook for an uncaught exception; without the file the script runs as before. Only an internal error is recorded: never one of MACH's own exception classes (a refusal), `SystemExit` (usage errors, every exit code), `KeyboardInterrupt` or a broken pipe. The hook then hands the exception on unchanged, so stderr and the exit code are what they were; a failure to record is silent. One private file per fingerprint (script, exception type, innermost MACH frame) in `.factory/local/faults/`, counted when it recurs, at most 50; nothing where there is no `.factory`.
* **Files from different versions are not a defect (0.20.1)**: where the installer put MACH in a project (`.claude/skills/mach-*`), an uncaught `AttributeError` or `ImportError` raised for one of MACH's own modules means one MACH script asked another for something an older copy does not have. The hook then prints one line, `MACH: MACH's files in this project are from different versions; run the installer again.`, shows no traceback, records nothing and leaves the exit status at 1. A record of such an error made under an earlier installed version is no longer counted or offered for a report. In a plugin or MACH's own repository every file comes from one version, so the same error is recorded as any other.
* **What a record holds**: MACH's version and install kind, the script, sub-command names (never values), the exception type, MACH's own frames (path inside MACH, line, function; no source line, no local), the message scrubbed (secret shapes and the shared redaction, addresses, paths outside MACH, every argument, environment, user, host, project, remote and ticket value, and every word that is neither MACH's nor Python's), the platform, Python, and whether it ran in a supervised execution.
* **The offer**: while an unreported fault exists, `next` and `status` (the digest's `faults`) and `doctor` add one fixed line. The doctor still never opens `.factory/local/`: `run.py doctor` reads the records and hands it the check (`faults`, by fingerprint and count) and the line.
* **Report**: `run.py report [<fault-id>] ["<words>"]` builds the title and body from a fixed template (the person's words bounded and made inert; the doctor's checks by name and state only), redacts and scans the finished text and refuses it if a secret shape remains, and prints it with a code that expires in ten minutes; `--confirm <code>` files exactly that text (by its hash) with `gh issue create` on `report.repository` (default `swiftj/mach-harness`, owner/name on github.com), adding the `mach:self-report` label only where it already exists. An open issue carrying the same fingerprint gets a short fixed comment instead (`--new` for a new issue). Without `gh`, signed out or without access, it gives the `--print` text and a plain sentence. The record is then marked reported with the issue's address.
* **Never**: automatic, inside a supervised execution, called by a station, agent, workflow or the supervisor, or with repository names, ticket or spec text, file contents or environment values. `report.enabled: false` in the tracked settings removes the offer and refuses the command.

### The Factory Floor

A read-only view of the Factory in the browser. Three workspaces: Line (the default, key `1`), Floor (the isometric Factory Atlas, key `2`) and Analytics (key `3`). It shows the Factory as it is now: there is no playback, playhead or replay. Code: `apps/observer` (Go, standard library only) and `web/apps/factory-floor`. Design: `docs/mach-next/M6_1_OBSERVER_DESIGN.md`, `M6_1_EVENT_CONTRACT.md`, `M6_1_SHARED_CONTRACTS.md`, `M6_1_STATION_TELEMETRY.md`.

* **Lifecycle log (M6.1)**: each station appends one line to `.factory/worktrees/<ticket_id>/lifecycle.jsonl` (`station.entered`/`exited`, `gate.evaluated`, build tasks, verification checks, review rounds and verdicts, human approval, merge, cleanup) through one helper, `skills/intent/scripts/lifecycle.py`, after the station's own write. A failure to record changes no exit code, output or station file; the station files win on any disagreement. Cleanup's records go only into the archived copy.
* **The observer (`mach-observer`)**: follows the intake event log (versions 2 and 3; a version 3 line names its epic and the slice's issue and no project, which stays absent; a version 2 line's wave is dropped, so an older history's slices show without a group), every cell's lifecycle log, execution streams and the archive; normalises them to event schema 3 (revision 4, M11: `ids.epic_id` and `ids.issue` in place of `ids.wave_id`, no `wave.discovered`, and `slice.materialized` carries the epic's name from the intake ledger as `epic_title`, free text under the display policy), redacts before indexing, and keeps its index under `.factory/local/observer/`. It serves a versioned GET-only API (`/api/v1/...`), a server-sent event stream and the embedded Factory Floor on `127.0.0.1` behind a one-time link. It starts no process, runs no MACH script, takes no MACH lock and connects to nothing, so stopping it never affects the line. Evidence images and video are served only when `floor.evidence_media` is true in `.factory/config.json`.
* **Started by a skill step, not a script command**: asked to "open the Factory Floor", or given `/mach floor`, the run skill starts `.factory/bin/mach-observer --project <root>` (or a checkout's own build), opens the printed one-time link in this machine's browser itself (`open`, or `xdg-open` on Linux), and reads `.factory/local/observer/link` for a second browser. The observer still starts no process: the skill opens the browser. `run.py` has no command for it; no station, agent or workflow calls it (`tests/test_mach_floor.py`).
* **Shipping**: built per platform by the `release` workflow with the Factory Floor embedded, smoke-tested with `apps/observer/smoke.sh`, listed in `SHA256SUMS` and attested; the installer fetches it like `mach-studio` (`--no-floor`, `MACH_FLOOR=skip`, `MACH_FLOOR_URL`). The 0.13.0 release candidates carry it; v0.12.0 and earlier have none, and the install then succeeds with a one-line note. The macOS programs are not notarised.
* **The Line**: the default workspace (`#line`): stations left to right as columns (Groom, Plan, Build, Verify, Review, Merge, Clean up), each ticket a row at its station. A "Needs you" strip lists tickets waiting for a person or stopped; each state (working, held, waiting for a person, stopped, landed) has its own shape as well as colour, and work sent back is a dashed arc. A ticket's row, side panel and full record show its issue number (as text; nothing links outside the page) and its epic's name (free text, contained) where recorded. Selecting a ticket shows why it is there, what it needs from a person, where the time went, its recorded cost and the real `/mach` command to copy (`decide`, `explain`); selecting a station shows its worker, the models recorded there and its typical time; a double-click or Enter opens the ticket's full record, station by station, from which the evidence player opens. Only recorded data is shown: a typical time is the median of the measured visits the page holds, a held reason appears only when one was recorded, a missing cost reads "not recorded", and nothing is estimated. Code: `web/apps/factory-floor/src/line/`. The observer still serves `/api/v1/spans`, `/marks`, `/history`, `/series` and `/snapshot`, which the page no longer uses (`/api/v1/concurrency` is still used by Analytics).
* **Factory Analytics (M6.5)**: the Analytics workspace (`#analytics`, key `3`): how well the Factory operates, where time and rework go, and what is recorded as spent. Seven areas over one set of filters (the epic is a filter and grouping on T1, T2, C3, C4, W1 and W2; M11 retired T3 "Waves delivered" and C5 "Wave lead time", with no replacement: slices integrated per epic is T2 by epic, slice lead time is C4) (Pulse, Flow and bottlenecks, Quality and remediation, Agent and model economics, Reliability and autonomy, Compare, Improvement opportunities). It extends the observer's existing metric engine (`apps/observer/internal/metrics`, the catalog in `docs/mach-next/M6_1_SHARED_CONTRACTS.md`); there is no second engine and no catalog ID is renamed. Observer routes, GET only, under `/api/v1/analytics/`: `metrics` (time windows, `last_runs`, two-way grouping, trend buckets, distributions, basis counts, coverage), `flow`, `contributors` (the entities behind a figure: identifiers, codes and numbers, never prose), `runs`, `insights` (deterministic rules, advisory); all take one cursor (`at`) per view and an as-of time. Every figure carries its sample, coverage and basis; a missing value is never zero; recorded cost is never divided among agents or stations. The observe station's scorecard metrics match `observe.py` (`tests/test_mach_analytics_parity.py`). Code: `web/apps/factory-floor/src/analytics/`, `apps/observer/internal/insight`, `internal/project/flow*.go`. Design and limits: `docs/mach-next/M6_5_DESIGN.md`, `M6_5_SECURITY.md`, `M6_5_TESTING.md`, `M6_5_ACCESSIBILITY.md`.
* **Execution provenance (M6.5)**: when the supervisor starts an execution it records one snapshot of what the run was started with (`skills/run/scripts/provenance.py`): MACH's version, a digest per skill, agent and workflow file, the configuration's digest and a `config_id`. Digests, versions and identifiers only. It is captured after authorization and cannot change whether or how an execution starts; a failed capture is recorded as such. Executions from before it read as not recorded.
* **Evidence player (M6.4)**: what the verifier captured, shown beside the check it proves. It opens for one ticket from a cell's inspector, a check in a verification gate, an artifact a check cites, or a verification visit in a ticket's full record on the Line: checks grouped by verification run, the files of the selected check, and a viewer for images, video (the browser's own controls, never autoplay) and text (transcripts, logs, JSON and `.http` dumps, as plain monospaced text). It is a reader of routes the observer already had (`/api/v1/cells/{ticket}/evidence`, `/api/v1/artifacts/{id}/content`): content loads only when a person selects a file, by catalog ID, never ahead or in bulk; text is never rendered as markup; nothing the catalog withholds is offered, and each reason is said in plain words; a file that does not match its recorded hash says so and is never shown as proof. Images and video still need `floor.evidence_media`. The page's policy gained `media-src 'self'` for it, and a check from an earlier verification run resolves to its own run's file. The Simulation shows sample content the app draws itself, labelled as such. Code: `web/apps/factory-floor/src/evidence/`. Design: `docs/mach-next/M6_4_EVIDENCE_PLAYER.md`.
* **One product (M6.6)**: the three workspaces share one source state (Live Factory, Simulation, stale, disconnected, a source unavailable, history incomplete). Figures counted by whole UTC day say which day they stop at. Every field the observer declares as free text (`display_policy.free_text`) is shown plain, bounded and labelled as not checked for names (names in it are shown, not removed), and never placed in a tooltip, an accessible name, the address or storage. Checked against real supervised runs. Acceptance: `docs/mach-next/M6_6_ACCEPTANCE.md`.

### Release qualification (`/mach release`)

`skills/run/scripts/qualify.py`, reached as `run.py release status|qualify|show|except`, evaluates an epic (`release qualify --epic <EPIC-ID or issue number>`) or a named list of slices (`release qualify SLICE-001 SLICE-002`) at one exact commit of the integration branch and writes a deterministic snapshot, `.factory/release/<release-id>/readiness.json` (schema `docs/mach-next/schemas/release-readiness.v2.schema.json`). An epic's slices are those this Factory took in for it, those whose spec header at the commit names it, and those its issue lists; one it lists but never took in is `missing`. Design: `docs/mach-next/M7_RELEASE_QUALIFICATION.md`, `M11_DESIGN.md` section 6.

* **Evidence, not prose**: each slice's spec at the commit (its header taken off, matched by SHA-256 to the revision this Factory built, and passing the intent gates), its ticket, integration (checked in Git), verification verdict and review decision from the archived run record; every `AC-NN` mapped to its recorded evidence; the test suite rerun at that commit on a clean tree with the audit station's runner; contracts unchanged since review approved them; dependencies integrated; no newer approved revision left out; integration tests (`release.integration_command`) and performance if declared; open review blockers and scanner reports (`.factory/release/scans/`).
* **Outcome**: `blocked` (a failing check or open blocker), else `incomplete` (a required check missing, not run or not configured: never a pass), else `qualified_with_exceptions` (each gap carries a person's exception for this exact commit, `release except`, only on their explicit word), else `qualified`.
* **Product acceptance, per epic**: Product Studio's `acceptance record` posts a fixed-template comment on the epic's issue, bound to the release ID and its commit; accepting needs a qualified snapshot. The snapshot reads it through `ticket.py epic-check` and reports `accepted`, `rejected` or `not_recorded`: a comment counts only when written by the account it names, unedited, by someone with the triage role or above; the latest that counts decides; it is never inferred. A release of named slices records no acceptance.
* **Never**: merges, pushes, tags, deploys, starts a station, or reads the machine-local Factory settings; no station, agent or workflow calls it.

### Factory evals (`/mach eval`)

Past tickets kept as a suite and replayed when the Factory's own rules, skills, agents or model tiers change. `skills/observe/scripts/evals.py`, reached as `run.py eval collect|add|status|run|compare|show`. Design: `docs/mach-next/M14_DESIGN.md` part B; as built: `docs/mach-next/M14_FACTORY_EVALS.md`.

* **Cases**: `eval collect` reads merged tickets' archives (only the cell's own records, never evidence media or bundles) into `.factory/evals/cases/<case-id>/`: the spec as text and data, the intent, the base commit (where the branch left the default branch), and the recorded outcome (verdict, rounds, deviations, test names); redacted with the ticket station's shared rules. Shared by Git; runs are git-ignored. `eval add --from-ticket <T> --reason` makes an escaped defect a case whose reason is a holdout check for the replay's verifier; `--spec --base` adds one by hand; `--must-pass` marks one, on a person's word.
* **Status**: the configuration under test (rule files, MACH's line digest from `provenance.line`, model tiers) from the main checkout or, with `--ticket`, a cell's branch head; what changed since the last run, by digest.
* **Run**: `eval run --plan --budget <USD>` lists the cases, the ceiling, the boundary and the execution risk, spends nothing, and gives a code; `eval run --confirm <code> --accept-execution-risk`, on a person's yes, replays each case from planning through verification (the belt stopped before review) in a throwaway clone under the system's temporary folder: fetched from the project with no remote, `protocol.allow never`, local tickets, manual merge, supervisor and notifications off, the configuration laid over the base commit. One execution per case through the executor's own boundary (restricted, no MCP, prompts refused, `policy.default_tools()`, a spending limit per case, a session ID); the clone's ledger scopes `run.py` to the one ticket. Removed afterwards unless `--keep`. Per case: planned, built, verdict, rounds, deviations, time and recorded cost; per run, the provenance snapshot.
* **Compare**: deterministic; only a recorded PASS is a pass, a missing value never is; `must_pass` cases not passing are listed.
* **Never**: started by a station, agent, workflow, hook, timer or the supervisor; run inside a supervised execution (`collect`, `add`, `run` refuse); reads `.factory/local/runner.json` or enables the Factory; touches the project's checkout, GitHub, review or merge. No real model run has been made with it yet.

### Merge station: `/mach-merge`

Step 6 of the belt. `skills/merge/scripts/merge.py` lands exactly what review approved, or refuses.

* **Commit-bound approval**: review records the commit it approved. If the cell's branch is no longer that commit, the approval is voided and the cell returns to `built` to be verified and reviewed again. An approval that rests on a person's security exception is bound the same way (the voided round keeps its exceptions on record), and the merge station's own revalidation keeps both as it keeps the approval. An exception past its expiry stops the merge, changing nothing: the ticket waits for a person (`security-exception-expired`). The pull request body lists each exception with who accepted it and why, and the approvals before and after when it cleared a reject vote. It also carries a "Security scan" section: each secret candidate (file, line, kind) and each added or changed dependency with the security seat's answer, or a line saying the scan was off; never a value.
* **Revalidation (merge queue)**: if the main branch has moved since approval, main is merged into the ticket's branch inside the cell and the test suite is rerun on the result. A failing suite returns the ticket to the build station with the failure as findings; a conflict stops for a person. When the merge is clean and the suite passes, what landed in between is checked too (M13): a landed commit that changed a file this ticket also changed (its diff from its merge base, leaving out the change record folder, other slices' specs and byproducts), or a landed slice whose effects section changes, replaces or retires a shipped rule this ticket's spec lists or one of a slice it depends on (`cell.json` `product.depends_on`), voids the approval: nothing lands, main stays merged into the branch, the reasons go to `review/merge-recheck.md`, and the ticket is verified and reviewed again on the merged result. A pass uses no judging round (the re-review is round-N.1); a failed re-verification counts as any failed verification. `merge.revalidate_overlap: false` turns the check off. As built: `docs/mach-next/M13_MERGE_CHECK.md`.
* **The shared main (M20 A2)**: when the repository has an `origin` remote, `run` fetches `origin/<into>` first (one branch; a fetch changes no checkout, like `--fetch` and the supervisor's `auto_sync`). If origin cannot be reached, or has no such branch, nothing is merged and the refusal says so (`remote-unreachable`, `no-shared-main`); there is no fallback to the local view. Then, by method: with `pr`, "main" above means `origin/<into>`, the branch the pull request merges into, and the revalidation, conflict check, test run and landed-overlap check are made against it (unpushed local commits are not on it and are not tested against). With `local`, the merge goes into this checkout, so the checks are made against the local `<into>` as before, unpushed commits included, but only once it provably holds the shared main: if `origin/<into>` has commits the local `<into>` lacks, nothing is merged and the refusal says how many and to pull `<into>` first. A local merge with a remote is never pushed; the result's `note` says it is on this machine only and must be pushed for others to get it. `plan` reads origin as last fetched and fetches nothing; its `compared_with` names what it compared with. With no remote, nothing changes.
* **Closing the window (M20 A2)**: with `pr`, just before `gh pr merge` the station reads origin's `<into>` again (`git ls-remote`). If it moved since the revalidation, nothing is merged; the result's `main_moved_again` says "origin/<into> moved again (now …); re-validating", and the station fetches and revalidates on the new main (the change record already on the branch is kept, as for a pull request left open). The same happens when GitHub refuses the merge and origin's `<into>` has moved (an "up to date" rule). At most `MAX_MAIN_MOVES` (2) re-validations in one run; a third move stops with `main-moving`, the pull request left open. The merge itself stays bound to the head commit (`--match-head-commit`); GitHub offers no guard on the base, so after merging the station compares the merge commit's first parent with the commit it tested on and, if they differ, the result carries `untested_base` and a plain `warning`. Only GitHub's "require branches to be up to date before merging" closes that last instant; the doctor's `merge.protection` check says whether it is on.
* **The change record (M13)**: as its last act before landing, the station writes `docs/changes/<ticket>.md` (`records.dir`; `records.enabled: false` writes nothing and the pull request says nothing of it) on the ticket's branch and commits it alone, so it arrives in the same merge commit or pull request as the change. Text only, deterministic and bounded: the why, slice, revision, epic and issue; since M15, only where the spec has the section, the product principles it answered, the policy packs with their digests and each concern's resolution (who accepted it and how the name was checked), and its effects on shipped behaviour (from `spec.json` and `cell.json`); the plan's tasks, the ADRs in force (IDs, digests) and any ADR exception; every verification run, each scenario and rule with the name and SHA-256 of its evidence files (earlier failed runs included); every review round (votes, findings, a person's approval or send-back, security exceptions with reasons, the scan's answers); the builder's overrides; the approved, revalidated and base commits. Free text is redacted by `issue_rules.py` and made inert (no mention, issue link, closing keyword, HTML or Markdown link); the scan's secret shapes mask what remains, and anything still found refuses the record and the merge. The evidence files stay in the local archive. The approval stays bound: the station accepts its own record commit only when it adds or changes exactly that file on top of the approved or revalidated commit (`change_record.holds`, also used by `run.py next`); any other commit voids the approval. `records.dir` inside the ADR folder is refused. The pull request body links to the record at the commit that added it. As built: `docs/mach-next/M13_CHANGE_RECORD.md`.
* **Method**: `local` (the default) makes a merge commit on the main checkout and never pushes; with a remote it first requires the local main to hold the shared main (above). It suits one person; the doctor's `merge.method` check warns when GitHub shows more than one person who can push. `pr` pushes the branch, opens a pull request whose body summarises verification, review and build, and merges it with the platform told to accept only the approved commit.
* **On the pull request (M9, M11)**: the body refers to the slice's own issue with `Refs #<n>`, never a closing keyword: the Factory closes a slice's issue itself once it sees the merge on the integration branch. Unless `merge.pr.inline_findings` is `false`, the approving round's findings are posted once as one review: inline where the line is in the diff, otherwise in its summary, each with its seat, severity and the rule it cites. Reviewer text is redacted and bounded, and mentions are broken. A failure to post never blocks the merge.
* **Jira key (M13)**: a slice's Jira key (`cell.json` `product.jira`, checked against Jira's form again) goes at the start of the pull request's title and of the local merge commit's message, and into the change record's header; `tickets.jira.browse_url` (https, no credentials, ending in `/`) makes it a link in the pull request body and the record, and a malformed one refuses the merge. Nothing calls Jira. As built: `docs/mach-next/M13_JIRA.md`.
* **A small change (M18)**: the change record's ticket line and the pull request's ticket line say "a small change" beside the ticket (`cell.json` `kind`), and its title reads `<ticket> (small change): ...`; a small change that became a full slice says "a full slice that began as a small change" with the rule's fixed sentence (`widened.reason` when a rule decided), or that it was made one on a person's word, whose words are not repeated; its title is a full slice's. Every other ticket's record and pull request are as before (`change_record.small_change_words`).
* **Policy** (`merge` in `.factory/config.json`): `mode` `auto` or `manual`; `auto.<tier>` to keep a risk tier for a person. `--by-person` lets a person merge whatever the policy. High-risk tickets still need a person's approval in review unless the review settings say otherwise.
* **Never**: force-pushes, rewrites history, deletes a branch, or merges into anything but the default branch.

### Architecture decisions (ADRs)

Engineers record technology decisions (stack, libraries, languages, component structure, API contracts, security standards) as MADR files, `docs/adr/NNNN-title.md` (`adr.dir` in `.factory/config.json` moves the folder), and change them only by ordinary pull requests. Only `status: accepted` binds. MACH reads one extra header field, `applies-to`: `path:<glob>`, `app:<app_type>`, `topic:<word>` or `all` (missing means `all`). One shared helper, `skills/intent/scripts/adr.py`, finds, parses, lists and selects them for a cell, reading the main checkout's committed state plus the ADR files the cell's own branch added; a malformed ADR is a problem with its reason, never silently accepted or ignored. Design: `docs/mach-next/M11_DESIGN.md` section 7; as built: `docs/mach-next/M11_ADRS.md`. MACH's own `docs/mach-next/ADRS.md` is unrelated.

* **Plan**: the contract engineer reads them with `cell.py adrs`. `check-plan` refuses a plan that names an ADR that does not exist or is not accepted, or whose file touch map falls under an accepted ADR's `path:` globs without naming it or a person's recorded exception, and any plan task that changes an ADR file. It records in `cell.json` the ADRs (ID and digest) the plan was made under and keeps a copy of each text in the cell.
* **Cannot comply**: `cell.py adr-conflict` records which ADR and why; the routing sheet stops (`adr-decision`) and the walkthrough offers what the scripts accept: a person's exception (`cell.py adr-exception --by --reason`, their words, shown to the builder and reviewers) or, once an engineer has superseded or changed the ADR, `replan`. Neither is recommended by rule.
* **The required baseline (decided 2026-11-18)**: no ticket is planned or built until every topic in `adr.required_topics` (default `language`, `framework`, `storage`, `testing`, `deployment`, `coding-standards`, each with one fixed line in `adr.py`) has an ADR that is accepted, committed on the main branch and names `topic:<name>`; an ADR that decides a topic does not apply covers it, a malformed one never does, and an empty list is the project's only "off". `run.py next` stops at `spec-ready` (`adr-baseline`, with `missing_topics`); `cell.py claim <ticket> plan` and `check-plan` refuse for the same reason. Grooming, cells already planned and `factory-tuning` tickets are not held; `repo-hardening` tickets are, since hardening chooses the test runner and linter. `/mach adr baseline` (`run.py adr baseline`, `baseline.py`) gathers evidence read-only from the main checkout's committed files, redacted and bounded, records it once per topic in the git-ignored `.factory/adr-baseline.json`, and the skill writes one `proposed` ADR per missing topic with `run.py adr new --baseline <topic>` (evidence listed, open points marked; no evidence means asking the engineer). It never redrafts a topic that has an ADR. `/mach adr accept <ADR-NNNN>... --by` sets proposed files in the working tree to accepted, on an engineer's word, and commits nothing.
* **No ADR covers a needed choice** (outside the required topics): the contract engineer drafts a `proposed` ADR on the ticket's branch (`cell.py adr-draft`) and the plan lists it. Low and Medium risk go on and the proposal is reviewed with the change; High risk stops (`adr-acceptance`) until a person accepts it (`cell.py adr-accept --by`, which sets the status on the branch copy and commits it there).
* **The baseline is an interview**: `/mach adr baseline` does not stop at a list of open points. The run skill settles each with the engineer by the intent interview's method, one yes-or-no question at a time with a recommended answer; facts are looked up in the repository and recorded without a question, a conflict in the evidence is the question, and a point is left undecided only on the engineer's word. Each answer is written into the draft by `run.py adr settle <ADR-NNNN> --point <n> --answer "<text>" [--decision "<text>"] [--not-decided]` (proposed ADRs in the main checkout's working tree only; refused inside a supervised execution), never free-hand. A second run resumes and redrafts nothing. When nothing is open it asks once to accept, then offers to put the decisions on the main branch the project's way and names the tickets waiting. MACH itself needs only the commit on the main branch, never a review; `adr.landing` says how a project gets it there: `pull-request` (the default, for a team: a branch and a pull request) or `main` (one engineer: a commit to the main branch). Either is done only on the engineer's word, and the other way may be chosen for one occasion. `adr accept` refuses a draft with an open point or an empty decision.
* **Technical needs as evidence (M17)**: the baseline also reads the technical needs the product manager published and committed on the main branch (`product/ready/NEEDS/needs.json`, at the same commit as the code; only `active` needs). A fixed table in `baseline.py` says which kind informs which topic (`people` and `connections`: framework, deployment; `data`: storage, deployment; `never`: storage, testing, deployment; `priority`: language, framework, storage, deployment; `given`: every topic, a project's own included). Each item names its source (`need:TN-03 revision 2`), redacted and bounded, and a `given` says who stated it and when. Needs are read again on every run and never kept in `.factory/adr-baseline.json`, so a need published after a topic's code evidence was recorded is not lost. A topic whose only evidence is needs is `from_product`: the skill drafts it from them with at least two options, consequences in product terms, and each given turned into an open point to confirm; the report lists every active need once with the published revision and hash. An ADR names the needs it serves in one more optional header field, `serves: TN-01@2, TN-04@1` (malformed is a problem, as for `applies-to`); `run.py adr new --serves TN-NN` accepts only an active published need, writes its revision, and requires two `--option` entries. `adr list` flags an accepted or proposed ADR that serves an older revision, or a need retired or missing, in a sentence; nothing is blocked or reopened. A missing needs file is today's baseline; a malformed one is reported with its reason and used for nothing, and so is one whose `sha256` is not the SHA-256 of the needs it holds (recomputed with the ticket station's `issue_rules.needs_folder_check`, over the needs as stored), so a file edited by hand after it was published is never used. A need never covers a topic: only an accepted ADR does. Design: `docs/mach-next/M17_DESIGN.md` part C.
* **Brought-in designs as evidence (M17)**: the baseline also reads each design the product manager published and committed (`product/ready/DESIGN/DES-NN/design.json` and the document beside it, read from git at the same commit). A topic the design maps `decided` or `partly` gives one item citing its lines (`design:DES-01 lines 40-52, 60`) with the summary and, for `partly`, what is missing; `silent` gives none. A topic whose only evidence is needs and designs is `from_product`. The document is checked against the recorded `sha256` and `lines`; a malformed or mismatching design is listed in `designs_problems` with its reason and used for nothing, never a crash. The report's `designs` carries each design's per-topic states, its decisions outside the required topics (`other`) and the conflicts the product manager settled `ask-engineer`, redacted and bounded: the skill drafts a `decided` topic from the cited lines, turns `partly` and `silent` into open points, asks the engineer each `ask-engineer` conflict, and offers each `other` decision as an `adr new` draft, never written unasked. Designs are read on every run and never recorded; `adr new --baseline` lists the design lines among its evidence. A design never covers a topic.
* **The engineer's own technical documents (decided 2026-11-23)**: an engineer who already has technical documents (an ARCHITECTURE.md, a high-level design, stack, deployment or coding-standards notes, ADRs in another format; Markdown or plain text, inside the repository or anywhere on the machine) names them, and the baseline drafts from them beside the code. This is the engineer's route; the product manager's design route is unchanged. `documents.py` (run skill) holds it, reached through `run.py adr baseline`: `--from <file or folder>...` names them (a folder gives its `.md`, `.markdown`, `.txt` and `.text` files; hidden and build folders are skipped; a PDF, an image or a symbolic link in a folder is listed as not read); `--show DOC-NN [--lines A-B]` prints one numbered, redacted, bounded and fenced (`<<<TECHNICAL-DOCUMENT-DATA ...>>>`) as data; `--map <json>` records the model's map; `--decline N...`, `--forget DOC-NN` and `--no-documents` record the engineer's word. The documents are never edited, moved, copied or committed. `.factory/adr-baseline.json` keeps, under `documents`, each one's path (and its place as people read it: relative to the repository, `~/...`, or in full), SHA-256, bytes, line count and sections, the map, and which ADR was drafted from which document versions. Bounds: 20 documents, 512 KB and 20,000 lines each, 2 MB together, 5,000 entries walked in the folders named; naming is all or nothing, and a PDF, a binary, a non-UTF-8 file, an empty file, a symbolic link or a missing path named directly refuses the call with a plain sentence. Naming the same files again records nothing; the same text at another path is not named twice. Every report, show, map and draft reads each document again and compares its SHA-256: a changed or missing document is said in `documents.changed`, used for nothing until it is named again or forgotten, and then the map is made again; an ADR drafted from the earlier text is named so the engineer checks it. The map, proposed by the model and checked by the script as `design map` is, covers all the documents at once: per required topic `decided`, `partly` (with what is missing) or `silent`, citing documents and line ranges; every other decision (title, summary, lines, `applies_to`, and `original` for an ADR written in another format; a required topic is refused there); and every conflict, tied to a topic or another decision, between two places in the documents or `against` a committed file, an active published technical need or a published design. A map that leaves out a required topic, names an unknown one, cites a document or lines that do not exist, or names an unknown need, design or file is refused whole with every problem, recording nothing; text is one line, redacted and bounded, with no fence marks. Reading, sections, line ranges, one-line fields, the map file's bound and the fence are `prd.py`'s, shared by path. Once mapped, a topic the documents decide gives an evidence item (`documents: DOC-01 ARCHITECTURE.md lines 6-7`); one whose only evidence is theirs is `from_documents`. `adr new --baseline <topic>` (refused while documents are named but not mapped as they are now) adds each cited document's place, SHA-256 and lines to the ADR's evidence, and the missing part and every conflict on the topic as open points; `adr new --document-decision <n>` drafts another decision the same way (the map's `applies_to` when none is given), once. The report offers the other decisions as one list (to offer, drafted, declined); a new map keeps the engineer's earlier yes and no for the same decision. Conflicts are settled in the interview, never by MACH; one against a technical need names the need and says the product manager owns it. The report's `next` leads the engineer through in order (ask for documents, read and map, draft, offer, settle, accept, commit) and `baseline_covered` says when every required topic is covered. Refused inside a supervised execution, like the rest of the baseline.
* **The architecture overview (M17)**: `run.py adr overview` with no content reads only and reports what the overview is built from (the active needs, every accepted and proposed ADR with its topics, status, title and `serves`, the designs), where it goes, and whether the one there is behind: an ADR accepted, superseded, changed or added since it was written, judged from a marker the script writes listing the ADR IDs and digests it was written from. With `--context`, `--parts` (a Mermaid `flowchart`) and `--data-flow` (a `sequenceDiagram` or `flowchart`) and an optional `--note`, it writes `docs/architecture/overview.md` (`adr.overview` moves it; a setting outside the repository, in `.factory` or the ADR folder, or not `.md`, is refused) in the main checkout's working tree: a title, one fixed line saying the ADRs are the authority and this is a map of them, the context, "What the product needs" and a table of ADRs by topic written by the script, and the two diagrams, both held to `diagrams.py`. The skill writes the context and diagrams only from accepted and proposed ADRs, offers the overview once the baseline's ADRs are drafted or accepted and again when it is behind. It commits and accepts nothing and is refused inside a supervised execution. No station reads it and no plan is checked against it.
* **Diagrams**: a Mermaid diagram may be drawn in an ADR and in `plan.md`, only where the structure or the sequence is the decision (component boundaries, a data flow, a sequence between parts, a state machine, a data model); GitHub draws it where the ADR is read. One shared helper, `skills/intent/scripts/diagrams.py`, checks what an agent wrote: `check-plan` for the plan and the ticket's own proposed ADRs, and `run.py adr new --diagram "<Mermaid source>"`, which draws it under the decision. Allowed kinds are `flowchart`, `sequenceDiagram`, `stateDiagram-v2`, `erDiagram` and `classDiagram`; at most two in a document and 40 lines each; no link, click action, HTML or renderer directive. A script cannot parse Mermaid, so a diagram that passes can still be drawn wrongly. ADRs people write are not checked. Slice specs, `spec.md` and `intent.md` carry no diagram: the decision table and the requirements are the authority, and Product Studio does not draw Markdown.
* **Timing**: an ADR accepted or changed later binds tickets planned afterwards; work already planned is flagged in `next`, `status` and `explain`, never restarted or blocked, and a reviewer may not cite it as a blocker.
* **Commands**: `/mach adr list` (reads only; also each required topic, what covers it and what is missing), `/mach adr baseline [--from <file or folder>...]`, `/mach adr overview`, `/mach adr accept <ADR-NNNN>...` and `/mach adr new "<decision>"` (a short interview, then `run.py adr new` writes the file as `proposed` in the main checkout's working tree; the engineer commits it by pull request). *Numbers across a team (M20)*: `adr.next_number`, used by `adr new` and `cell.py adr-draft`, counts the main branch, the working tree, this machine's open cells, and the ADR files on every `origin/*` branch and fetched `refs/pull/*` ref as last fetched (open pull requests' branches among them); neither command fetches. Two engineers can still take one number in the same hour: then both files bind nothing, and the problem on each (in `adr list` and every refused plan) names the other file, the later one (by the commit that added it to the main branch) and the exact command `/mach adr renumber <file>`. `run.py adr renumber <file>` (`adr.renumber`) gives that file the next free number: it renames it, changes its own `ADR-NNNN` mentions and, in the other ADRs and the overview, every reference by file name and the overview's row and marker entry for it; a bare `ADR-NNNN` elsewhere is changed only when no other ADR has that number, and otherwise listed in `check_by_hand`. It writes the working tree only, for the engineer to commit by pull request, and is refused inside a supervised execution.
* **Never**: the Factory, the observe station and `factory-tuning` tickets do not accept, change or supersede an ADR. The exception and accept acts are refused inside a supervised execution.

### Review rounds after the first

A revised ticket gets a delta review. The packet carries the diff since the previous round and the files that had blockers; `review.py submit` refuses a blocker on a file that neither changed nor was blocked before. Reviewers report a recurring defect once, as a class, and treat problems that pre-date the ticket as notes. Together with the three-round limit, this keeps review from re-litigating settled ground. When the build station merged main in at the revision (`build-report.json` `main_merges`, an entry whose `branch_commit` is the earlier round's head), the delta starts at that merge commit (`delta.main_merged_after`), so other tickets' work is neither shown as changed nor accepted as a blocker's file (M13).

## 6. Invariants the Factory's agents hold in a project where MACH is installed

These describe the product. They are not instructions for changing this repository.

1. **No Direct Master Commits**: All implementation occurs strictly within isolated cellular worktrees (`.factory/worktrees/<ticket_id>/`).
2. **Strict Test-First (TDD)**: No implementation code may be written until failing tests are committed and verified.
3. **No Speculative Completion**: An agent cannot self-certify completion. Passing to review requires objective artifacts produced by `/mach-verify`.
4. **Fresh-Context Reviews**: Code review sub-agents must always run in fresh context sessions to eliminate confirmation bias.
5. **Honor the 3-Loop Limit**: Never exceed 3 review-fix iterations on a single ticket. Escalate to a human engineer immediately upon a third failure.
6. **Preserve Boundary Contracts**: Component interfaces must be formally specified via Protocol Buffers (`.proto`) or OpenAPI schemas. Changing an existing contract requires a High Risk review pass; adding a new one is ordinary work.
